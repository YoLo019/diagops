## A. 架构设计类

### A1. 为什么要多 Agent?一个 Agent 不行吗?

**追问变种**:多 Agent 的优势到底在哪?是不是为了多 Agent 而多 Agent?

**口述答案**:
三个理由,都有对应的工程产出:

1. **上下文隔离**。日志、指标、部署是三类异构证据,塞进一个 Agent 的长上下文会互相稀释注意力。三个 Specialist 各自只接收与自己职责相关的证据,独立产出结构化 Finding,信息交换有明确的数据边界,而不是共享一条越来越长的对话历史。
2. **并行与故障隔离**。三个 Specialist 可以并行执行,单个失败不会取消其他任务——系统保留已成功的 Finding,明确记录是谁、以什么类别失败的。单 Agent 架构里一次失败就是整体失败。
3. **工具权限最小化**。按职责分配工具白名单:LogAgent 只有 read_logs,MetricAgent 只有 query_metrics/query_prometheus,DeploymentAgent 只有部署/服务目录/依赖三个工具。单 Agent 必然持有全部工具,攻击面更大。

同时我承认代价:协调复杂度和 token 成本都上升了。所以系统做了两件事来对冲:确定性 RCA 兜底(Agent 层整个关掉也能诊断),以及冲突才触发的二轮复核(不无脑重跑)。

**代码依据**:`backend/diagnosis/agents_runtime.py`、`backend/diagnosis/adaptive_tools.py`

**禁区**:不要说"多 Agent 准确率更高"——目前没有对比数据,OpenRCA
配对评测就是为了回答这个问题建的(跑完之前不声称)。

### A2. 为什么按日志/指标/部署划分,而不是别的分法?

**口述答案**:
按**证据领域**划分,而不是按"推理步骤"划分。每个 Specialist 对应一类数据源、一套工具权限、一种输出语义,职责边界和证据边界完全对齐。这样的好处是:某个领域的证据缺失时,能精确定位是哪一个 Specialist需要补采;某个领域的结论出问题,能定向复核,不动其他 Agent。

**禁区**:不要说 Specialist 之间会"讨论"或"协商"——它们不直接通信,所有交叉信息由 Coordinator 在二轮复核时定向注入。

### A3. Coordinator 做什么?它自己看原始证据吗?

**口述答案**:
Coordinator 负责三件事:初始协调(把故障事件和任务分发给 Specialist)、冲突处理、最终仲裁与根因排序。它不直接做证据采集,消费的是Specialist 的结构化草稿(SPECIALIST_DRAFTS)或校验后的 Findings(VALIDATED_FINDINGS)。二轮复核时,它把确定性基线、相关证据和peer findings 定向提供给被选中的 Specialist,再基于修订后的结果仲裁。

**代码依据**:`backend/diagnosis/coordination_review.py`

## B. 机制深挖类

### B1. "结构化 Findings"怎么保证模型一定输出合法结构?

**追问变种**:模型输出非法 JSON 怎么办?校验失败重试吗?

**口述答案**:
三层防线,层层递进:

1. **格式层**:工具用 Pydantic 模型生成严格 JSON Schema,约束模型输出;
2. **契约层**:对返回结果做二次校验,不合法不进业务流;
3. **语义层**(最关键):不只看 JSON 合不合法,还查业务语义——根因类型与证据 Provider 是否匹配、故障时间是否落在证据时间窗内、引用的Finding/Evidence 是否真实存在、同一证据是否同时被当作支持证据和反证、Agent 声称执行了生产操作时是否有真实人工作业记录。

校验失败不是无限重试,而是进入稳定的失败分类并降级到确定性 RCA。这是项目和普通 Structured Output demo 的本质区别。

**代码依据**:`backend/diagnosis/evidence_validation.py`、`backend/diagnosis/result_validation.py`

### B2. "冲突结论触发二轮复核"——具体什么算冲突?(必考)

**口述答案**:
四种触发条件,任一成立就触发,且只让相关 Specialist 进第二轮:

1. Specialist 结论与确定性 RCA 基线不一致;
2. 不同 Specialist 给出不同的根因类型;
3. Agent 明确提供了反证(contradicting evidence);
4. Agent 报告了阻塞性的证据缺口。

二轮时系统向被选中的 Agent 定向提供:确定性基线、相关证据、其他Specialist 的 findings,让它修订结论,最后 Coordinator 仲裁。设计动机是**成本**:不是所有 Agent 无条件重跑,而是冲突定向复核,节省模型调用。

**代码依据**:`backend/diagnosis/coordination_review.py`

### B3. "缺失结果定向补采"——缺失怎么判定?补采怎么做?

**口述答案**:
第一轮结束后,如果某个 Specialist 没有有效输出(失败、超时、输出未通过校验),系统只重新执行这一个 Agent,而不是重跑全部。补采过程
记录独立的 Round、Attempt 和 StepKind,审计时能区分"这是第几轮、第几次尝试、为什么重跑"。

### B4. "证据级仲裁"是什么?仲裁规则是什么?谁赢?

**口述答案**:
仲裁不是 Coordinator 自由心证,规则有明确的优先级:

1. **证据有效性优先**:引用无效证据 ID 的结论在校验阶段就被拒了,根本到不了仲裁;
2. **确定性基线对账**:Agent 结论与确定性 RCA 基线一致(agreement)时直接采纳;冲突(conflict)时进入二轮复核;复核后由 Coordinator 给出终裁(agent_leads 或 fallback);
3. **终裁不过就降级**:如果 Agent 链路整体不可靠,最终结果是确定性RCA 的输出,系统永远能给出答案。

一句话:证据说了算,基线做裁判,LLM 只是辩方。

**代码依据**:`backend/diagnosis/coordination_review.py`、`backend/rca/analyzer.py`

### B5. 根因排序的依据?置信度哪来的?

**口述答案**:
确定性 RCA 侧:每种故障模式是打分制(匹配到部署 +4、异常日志 +3、QPS 正常 +2……),分数映射为置信度,且有强匹配门槛(如发布回归必须同时有部署证据和异常日志),按置信度降序。都不匹配时返回 UNKNOWN(0.2 置信度)并附下一步该收集什么证据。Agent 侧:Finding 必须挂证据 ID,没有有效证据支撑的根因候选会被校验拒绝——置信度不允许脱离证据存在。

**禁区**:不要说置信度是"模型自己评估的"——模型自评置信度不可信,项目里的置信度都有证据打分或校验背书。

### B6. 某个 Specialist 挂了会怎样?

**口述答案**:
故障隔离是显式设计的:单个 Specialist 失败不取消同组其他只读诊断任务;系统保留已成功返回的部分 Finding,记录失败 Agent、失败分类(未配置/认证失败/限流/配额/超时等结构化枚举);如果缺失的是关键输出,触发定向补采;如果整个 Agent 层不可用(模型未配置、Provider异常、校验失败),自动降级到确定性 RCA,诊断链路不断。

**代码依据**:`backend/domain/multi_agent.py` 的 FailureCategory、
`backend/diagnosis/agents_runtime.py`

## C. 防幻觉与安全类

### C1. 怎么防止 LLM 编造结论?(必考)

**口述答案**:
设计前提是"LLM 输出是不可信输入",然后工程化围堵:

1. **强制引用**:每条 Finding、每个根因、每条建议必须挂有效证据 ID,引用不存在或不可用证据的直接拒绝;
2. **语义校验**:根因类型与证据来源匹配(说数据库慢就必须有指标类证据)、时间窗校验、支持/反证互斥;
3. **确定性基线对账**:Agent 结论要和纯规则引擎的结果比对,冲突触发复核;
4. **对抗测试**:验收集内置 Prompt Injection 探针,用真实工具调用记录判定越权,不相信 Agent 自述。OpenAI 基线成绩:注入成功 0、危险
   工具调用 0、错误一致结论 0。

### C2. 怎么防止 Agent 调用危险工具?

**口述答案**:
不靠 prompt 自律,靠代码边界:

1. 工具白名单按 Agent 显式分配,越职责调用直接拒绝;
2. 只允许只读工具,系统检查工具的只读属性;
3. 工具入参是严格 JSON Schema + 二次校验:不允许任意 PromQL、URL、
   文件路径、Shell、SSH、写操作;
4. 有界自主性:单 Specialist 最多 3 次工具调用、一次诊断最多 8 次、
   单次超时 10 秒、重复查询自动停止、没有新证据就停止。

**代码依据**:`backend/diagnosis/adaptive_tools.py`

### C3. 生产安全边界是什么?

**口述答案**:
全平台只读。不执行 SSH、回滚、重启、扩容、配置修改;建议是建议,审批记录只是记录,不代表执行;报告在没有验证记录时不允许声称
"已修复"。这个边界写在 AGENT.md 硬约束里,跨越它需要显式的长期目标变更和新安全 spec。

## TC. 工具治理类(对应简历第二条:自适应 Tool Calling)

> 简历条目:自适应 Tool Calling:按 Specialist 配置代码级只读工具白名单,
> 结合 Pydantic Strict Schema 与多维入参校验约束工具输入;以调用预算、
> 超时与自动停止机制限定 Agent 自主调用边界。

### TC1. "自适应"是什么意思?(本条最大考点,必背)

**口述答案**:
系统有两种策略:fixed 是诊断前一次性采好证据、Agent 只分析;adaptive
是 Specialist 根据当前证据缺口**自主决定**要不要再调工具补数据。
"自适应"指后一种——调不调、调什么,由 Agent 按证据情况决定,但
**边界由代码定**。
两种策略可以用相同模型、相同 prompt、相同案例、相同预算做配对评测
(OpenRCA fixed-vs-adaptive),用数据回答"自主性值不值"。

**禁区**:不要说"adaptive 效果更好"——配对评测未完成前无数据。

### TC2. 白名单"代码级"怎么强制?prompt 里写约束不行吗?

**口述答案**:
不靠 prompt 自律。每个 Specialist 在代码里显式分配工具集:LogAgent
只有 read_logs;MetricAgent 有 query_metrics、query_prometheus;
DeploymentAgent 有 read_deployments、read_service_catalog、
query_dependencies。Agent 请求白名单外的工具,在执行层直接拒绝——
这个拒绝不经过模型。系统还校验工具的只读属性。
核心原则:**安全边界必须建在模型之外**。

**代码依据**:`backend/diagnosis/adaptive_tools.py`

### TC3. "重复查询检测"怎么判定重复?

**口述答案**:
对工具名 + 规范化参数生成键,同一 Agent 提交相同查询会被识别并停止;
另一个相关机制是:工具返回了但没有产生新证据,也停止当前 Agent 继续
查询。两者都是防止模型陷入无效循环烧 token。
注意区分:重复检测是**防浪费**;运行时的工具幂等键是**防崩溃恢复后
重复执行**——面试官可能故意混着问。

### TC4. Strict Schema 严格到什么程度?模型传非法参数怎么办?

**口述答案**:
工具入参用 Pydantic 模型生成 JSON Schema,模型输出先过 schema,再过
二次业务校验:查询必须带合法时间窗口、服务范围、依赖目标、返回数量
上限。非法输入不会到达 Provider,而是变成结构化失败记录。
原则:Agent 无法构造任意 PromQL、URL、文件路径、Shell——它能选的
只有"查什么服务、什么时间窗",不能选"怎么查"。
(若没用 OpenAI strict 模式,被追问时说"schema 约束 + 服务端二次
校验",不硬撑 strict。)

### TC5. 预算数字(3 次/8 次/10 秒)怎么定的?

**口述答案**:
初始值来自对诊断轮次的估算:一个 Specialist 一次有效分析通常 1-2 次
补充查询足够,3 次给冗余;全局 8 次对应"三个 Specialist 各 2-3 次"的
上限;10 秒是只读查询的合理超时。这些值走配置可调,验收工件记录每次
运行的实际调用次数、成本和延迟,可据此再调优。

### TC6. 工具返回的内容可信吗?日志里藏指令怎么办?(高水平题)

**口述答案**:
项目前提之一是"**Provider 和工具的输出是不可信数据,不是指令**":
它进证据管道、被脱敏、被模型阅读,但永远不会被执行。验收集内置
Prompt Injection 探针专门测这一点,用真实工具调用记录判定越权,
不相信 Agent 自述。OpenAI 基线成绩:注入成功 0。

### TC7. 限制这么死,复杂故障 3 次调用不够怎么办?(压力题)

**口述答案**:
会有这种情况,这是有意的取舍:预算耗尽后 Agent 必须基于已有证据输出,
结论是低置信度 + "下一步该查什么",而不是无限烧钱。系统哲学是
"宁可是受限的诚实答案,不要不受控的昂贵猜测";需要时人工补充证据
再跑一轮。边界挡的是失控,不是能力。

### TC8. 这套治理和 OpenAI Agents SDK 是什么关系?

**口述答案**:
SDK 提供工具注册和调用循环的骨架;白名单、预算、停止条件、入参校验
是建在 SDK 之上的治理层。SDK 不管这些——这是"框架解决跑起来,治理
要自己建"的又一个例子(与 D1 题答案呼应)。

### TC9. 怎么测试这些边界真的守得住?

**口述答案**:
三层:单元测试覆盖校验逻辑;故障注入测试模拟工具超时/失败;真实模型
验收里有专门的越权探针和注入探针——用真实工具调用记录判定是否越权,
而不是问 Agent"你有没有乱来"。

### TC 背诵要点

- 一句定义:自适应 = Agent 自主决定调不调工具,但边界由代码定;
- 一张白名单表:Log→read_logs;Metric→query_metrics/query_prometheus;
  Deploy→read_deployments/read_service_catalog/query_dependencies;
- 三组数字:3 次/Agent、8 次/全局、10 秒超时;
- 一句原则:Provider/工具输出是不可信数据,不是指令。

## D. 压力与陷阱类

### D1. 为什么不用 LangGraph / CrewAI / AutoGen?(必考)

**口述答案**:
框架解决的是"跑起来"的问题,但项目的核心难点在框架之外:执行权管理(Lease/Fencing)、崩溃恢复(Checkpoint)、工具幂等、证据契约、确定性降级。这些需要对运行状态机有完全控制,框架的黑盒编排反而是障碍。同时项目并不排斥框架:保留了 OpenAI Agents SDK 作为可选执行层,和自研编排层可以配对对比——这是工程选型,不是框架偏见。

### D2. 多 Agent 比单 Agent 好多少?有数据吗?

**口述答案(诚实版)**:
目前没有定论数据,我不会编造。项目为此建了 OpenRCA 配对评测:fixed(纯证据预采集)与 adaptive(Agent 自主工具调用)用相同模型、
prompt、案例、预算跑同一基准,用数据回答"自主性值多少"。V8.2基线已冻结,V9 配对运行正在进行。我能给的数据是真实模型验收:
5 类故障 × 3 次共 15 case,OpenAI 基线 15/15 根因正确、15/15 证据引用有效。

**禁区**:不要拍脑袋说"提升了 XX%"。

### D3. OpenAI Agents SDK 的 handoff 和你的 Coordinator 有什么区别?

**口述答案**:
SDK 的 handoff 是控制权转移——一个 Agent 把对话主导权交给另一个。我的 Coordinator 不转移控制权,而是"收集-校验-仲裁"模式:Specialist输出的是结构化数据(不是对话),Coordinator 消费数据、按证据契约校验、按确定性基线仲裁。控制权始终在编排层手里,这和我"LLM 输出是不可信输入"的设计前提一致。
(面试前花一小时读 Agents SDK 文档的 agents / handoffs / guardrails /
tracing 四节,确保这题能聊细节。)

### D4. token 成本多少?值得吗?

**口述答案**:
成本是有界且可观测的:工具调用次数硬上限(3 次/Specialist、8 次/诊断)、10 秒超时、重复查询与无新证据自动停止;验收工件记录每次
运行的输入/输出 token、成本、延迟、工具调用次数。设计哲学是:确定性 RCA 免费覆盖常见模式,模型调用只花在真正需要综合分析的
地方,二轮复核只在冲突时触发——每一分钱都要有触发条件。

### D5. 这个项目有什么做得不好的?如果重做你会改什么?(必考)

**口述答案**:
三个真实的不足:

1. **确定性 RCA 只有 5 类硬编码规则**,覆盖面窄——它定位是兜底基线不是智能主体,但确实是当前诊断广度的瓶颈;
2. **证据源深度不够**:没有 Trace/调用链,没有代码 diff 证据,诊断只能到故障类型级,到不了代码级;
3. **缺标准基准的最终成绩**:OpenRCA 正式配对评测还在收尾。

改进路线我已经规划好:先跑完 OpenRCA 客观成绩,再接入 Trace 和代码 diff 作为受控证据,最后做带评测回归闸门的自进化机制。

## E. 评测类

### E1. 你怎么验证这个系统是对的?

**口述答案**:
四层验证体系:

1. **自动化测试**:1383 项 pytest,含 28 项运行时故障注入专项(Lease
   丢失、提交后崩溃、Checkpoint 篡改、恢复竞态等);
2. **真实模型验收**:5 类故障 × 3 次共 15 case,考 Structured Output
   合法性、根因正确性、证据引用有效性、工具越权、Prompt Injection、
   虚构生产操作——OpenAI 基线 15/15 通过;
3. **标准基准**:微软 OpenRCA 流水线,数据准备与 ground truth 隔离、
   工件冻结、SHA-256 完整性校验;
4. **运行时验收**:14/14 必需场景通过,含性能基线(恢复耗时约
   9.3ms,Runtime 开销 p50 +53%——可靠性成本是量化过的,不回避)。

### E2. 你的 15/15 可信吗?案例不是自己造的吗?

**口述答案(诚实版)**:

## F. 全域表述禁区(任何题都不能说的话)

1. ❌ "四个 Agent 共享对话上下文" → 实际是隔离上下文 + 结构化传递;
2. ❌ "多 Agent 准确率更高 / 提升 XX%" → 无对比数据;
3. ❌ "OpenRCA 正式效果已提升" → 配对评测未完成;
4. ❌ "DeepSeek 已通过认证" → Adapter 已实现,独立 Gate 未过;
5. ❌ "Agent 自动修复生产故障" → 全程只读,只出建议;
6. ❌ "Exactly Once" → 只能说"已持久化结果的幂等复用";
7. ❌ "Runtime 提升了性能" → 实测有 +53% 开销,买的是可靠性;
8. ❌ 置信度来自"模型自评" → 来自证据打分与校验。
