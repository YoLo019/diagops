# 29. OpenAI Agents SDK 使用详解与框架选型

## 1. 先给结论

DiagOps 使用 OpenAI Agents SDK，但只把它放在**模型执行层**：负责创建单个 Agent、运行模型—工具循环和解析结构化输出。跨 Agent 的阶段编排、Evidence 持久化、预算、超时、恢复和审计仍由项目自己的 Durable Runtime 管理。

```text
OpenAI Agents SDK
  └─ 单个 Agent：instructions + model + tools + output_type + Runner

DiagOps Runtime
  └─ 整次诊断：Lead → Investigators → Critic → validation
     + Evidence + budget + checkpoint + resume + trace
```

这不是“重复造一个 Agent 框架”，而是把职责分在两个不同层次：SDK 解决通用的模型调用问题，项目 Runtime 解决事故诊断特有的状态与可靠性问题。

## 2. 项目实际用了哪两个 OpenAI SDK

[pyproject.toml](../../pyproject.toml) 声明 `openai-agents>=0.18.1`，当前 [uv.lock](../../uv.lock) 解析为 `openai-agents==0.18.1`。运行时实际使用两层 SDK：

| 层 | 主要对象 | 项目用途 |
| --- | --- | --- |
| OpenAI Agents SDK（`openai-agents`） | `Agent`、`Runner`、`FunctionTool`、`AgentOutputSchema`、`ModelSettings`、`RunConfig` | Agent 定义、工具循环、结构化输出和模型抽象 |
| OpenAI Python SDK（`openai`） | `AsyncOpenAI`、Responses/Chat Completions client、SDK 异常类型 | HTTP transport、超时、连接关闭、usage 和异常分类 |

导入包名容易混淆：`openai-agents` 安装后使用 `from agents import ...`；底层 API SDK 使用 `from openai import AsyncOpenAI`。

## 3. V11 的真实调用链

```text
RuntimeCoordinator
  → DiagnosisPhaseExecutor
  → V11Runtime.run_phase
  → V11Runtime._call_model
  → Agent(...)
  → Runner.run(...)
       ├─ Model / ModelProvider
       ├─ FunctionTool
       │    → AdaptiveToolSession
       │    → ToolRegistry
       │    → ProviderRegistry
       │    → Evidence 持久化
       └─ output_type / AgentOutputSchema
            → Pydantic output
            → 引用、归属和发布条件校验
```

源码阅读顺序：

1. [V11Runtime._call_model](../../backend/diagnosis/v11_runtime.py)：组装 `Agent`、`ModelSettings`、`RunConfig` 并进入 Runner；
2. [_run_with_model_lifecycle](../../backend/diagnosis/agents_runtime.py)：实际调用 `Runner.run` 并采集模型生命周期；
3. [AdaptiveToolSession](../../backend/diagnosis/adaptive_tools.py)：把内部工具包装成 `FunctionTool`；
4. [ToolRegistry](../../backend/tools/registry.py) 与 [Provider tools](../../backend/tools/provider_tools.py)：调用数据源并生成 Evidence；
5. [V11 phases](../../backend/runtime/phases.py)：决定 Lead、Investigator、Critic 的执行顺序。

## 4. 项目使用的 Agents SDK 能力

### 4.1 `Agent`：定义一次角色调用

V11 为每个角色动态构造 `Agent`：

```python
agent = Agent(
    name=actor,
    instructions=prompt,
    model=sdk_model,
    tools=tools,
    output_type=output_type,
    model_settings=model_settings,
)
```

不同角色的契约确实不同：

| 角色 | Instructions | Tools | Output type |
| --- | --- | --- | --- |
| Lead | 规划信息缺口 | 无 | 任务计划 |
| Investigator | 调查一个具体问题 | 九个只读工具 | 候选根因 |
| Critic | 检查因果链、反证和替代解释 | 无 | 结构化审查 |

这符合 OpenAI 官方建议的拆分条件：只有当 instructions、tools、policy 或 output contract 真正不同，才值得增加 specialist；不是为了“看起来像 Multi-Agent”而拆角色。

### 4.2 `Runner.run`：执行模型—工具循环

`Runner.run` 负责一次 Agent 运行中的通用循环：

```text
发送模型请求
→ 模型可能返回 FunctionTool 调用
→ 执行工具并把结果返回模型
→ 模型继续运行
→ 得到 output_type 对应的最终输出
```

项目仍在外部增加三类约束：

- Run 级 model turn、Token 和 deadline；
- 每个 Investigator 更严格的 turn ceiling；
- 每个真实模型请求的 attempt、usage、失败类别和预算结算。

因此 SDK 的 `max_turns` 只是单次 Runner 边界，不能替代整个 Runtime Run 的耐久预算。

### 4.3 `FunctionTool`：把内部工具暴露给模型

`AdaptiveToolSession.tools_for` 将 ToolSpec 包装为 `FunctionTool`，包括：

- 工具名和描述；
- 压缩后的 JSON Schema；
- strict schema；
- timeout；
- `error_as_result` 行为；
- 实际调用回调。

但 SDK 只负责把模型参数交给回调。真正的安全边界仍在项目代码中：

```text
manifest/read-only
→ Pydantic 参数校验
→ 事故时间窗和实体 scope
→ duplicate/idempotency
→ Tool budget/deadline/lease
→ Provider 调用
→ Evidence 原子持久化
```

这也是项目没有直接使用任意 Shell、URL、PromQL 或 hosted tool 的原因。

### 4.4 `output_type` 与 `AgentOutputSchema`

Lead、Investigator、Critic 都返回 Pydantic 结构化输出。Agents SDK 负责把 `output_type` 转换成模型可用的 schema，并将结果解析为对应模型。

项目在 SDK 解析后继续检查：

- Evidence ID 是否真实存在；
- Evidence 是否属于同一次诊断；
- Candidate 与 Assessment 的归属是否一致；
- Critic 是否覆盖全部候选和检查项；
- 最终发布是否只包含 Critic 接受的候选。

所以 structured output 解决的是“格式可信”，不是“语义正确”。

### 4.5 `ModelSettings` 与 `RunConfig`

`ModelSettings` 用于：

- 控制 `tool_choice`；
- 对 strict output tool 强制工具输出；
- 将 SDK 层模型 retry 设为 0，避免和项目外层 retry 形成乘法。

`RunConfig` 用于：

- 设置 workflow name；
- 注入自定义 ModelProvider；
- 在 V11 中关闭 SDK tracing；
- 禁止 SDK trace 收集敏感输入。

SDK tracing 被关闭并不是“不做观测”。项目使用自己的 RuntimeEvent、AgentExecution、ToolCall 和 OpenTelemetry，因为这些记录要和数据库事务、Checkpoint、预算及恢复状态对齐。

### 4.6 `Model` 与 `ModelProvider`

项目支持两条模型 transport：

| 路径 | SDK 模型类 | 项目适配 |
| --- | --- | --- |
| 官方 OpenAI | `OpenAIResponsesModel` | [openai_model.py](../../backend/diagnosis/openai_model.py) 固定官方 endpoint |
| OpenAI-compatible | `OpenAIChatCompletionsModel` | [openai_compatible_model.py](../../backend/diagnosis/openai_compatible_model.py) 处理兼容 endpoint 和结构化输出差异 |

V11 还用自定义 `Model`/`ModelProvider` 包装模型请求，在真正发送前完成 Token reservation、turn 扣减和 lifecycle event，在响应后按 usage 结算。

### 4.7 `RunHooks`

历史兼容路径使用 `RunHooks` 捕获真实 LLM request 的开始和结束，记录 Token usage。V11 的主要预算与事件记录进一步下沉到 budgeted model wrapper，确保 SDK 内部每次真实请求都受同一 Run 预算约束。

## 5. 项目没有使用哪些 SDK 能力

### 5.1 没有使用 Handoff

OpenAI 官方将 Handoff 定义为“专家接管当前分支的会话控制权”。DiagOps 不需要某个角色接管用户对话，而需要：

```text
角色完成
→ 校验结构和 Evidence 引用
→ 持久化结果与 Checkpoint
→ Runtime 决定下一阶段
```

因此 V11 采用应用控制的 orchestration，而不是 Agent 自由 handoff。

### 5.2 V11 没有使用 Agents-as-tools

历史兼容路径曾把 Specialist 包装成 `agent.as_tool()` 交给 Coordinator。V11 主链路没有这样做，因为嵌套 Agent 调用会让以下信息更难单独控制：

- 每个角色的任务和归属；
- 并发 Investigator 的隔离；
- 每个真实模型请求的预算；
- 阶段级 Checkpoint 和恢复位置；
- Critic 前必须完成的持久化。

V11 由 Runtime 直接运行每个角色，角色之间只通过已提交领域对象交换信息。

### 5.3 没有使用 SDK Sessions

Session 适合保存多轮对话历史，但事故诊断的恢复状态不只是消息：还包括 ToolCall、Evidence、预算、阶段、租约和数据库事务。项目使用 SQLite Checkpoint，而不是把 Session history 当成事实源。

### 5.4 没有使用 SDK Tracing

V11 关闭 SDK tracing，避免原始 Prompt、模型输出或工具正文进入第三方 trace。项目自己记录：

- Agent/Model/Tool 生命周期；
- Token usage 和预算；
- Evidence ID；
- 失败类别；
- Checkpoint 与恢复关系。

### 5.5 没有使用 Hosted tools、MCP 和 streaming

- 九个工具都由项目本地定义和审计；
- 当前没有跨 Host 的远程工具发现需求；
- V11 使用非流式结构化结果，便于在一个明确边界完成校验、预算结算和持久化。

## 6. 为什么选择 OpenAI Agents SDK

### 原因一：抽象层次刚好

项目需要避免手写模型—工具循环，但不希望框架接管业务工作流。Agents SDK 提供：

```text
Agent + Runner + FunctionTool + structured output + Model abstraction
```

这些原语足以完成模型边界，同时允许项目保留自己的状态机。

### 原因二：结构化输出与 Pydantic 契合

项目的 Task、Candidate、Assessment、Decision 都使用 Pydantic。SDK 可以直接从 `output_type` 生成 schema，减少手写 JSON prompt、解析器和字段转换。

### 原因三：工具调用无需自行维护消息循环

Runner 已处理模型请求、FunctionTool 调用和工具结果回传。项目只需要专注于工具授权、Evidence 持久化与业务校验。

### 原因四：模型 transport 可替换

官方 Responses 和 compatible Chat Completions 可以实现同一个 SDK `Model` 接口，角色和 Tool Calling 代码不需要绑定某一家网关的消息格式。

### 原因五：可以关闭不需要的默认能力

项目可以关闭 SDK tracing、SDK retry，不使用 Handoff/Session，把安全和可靠性收回到本地 Runtime。

## 7. 与其他框架的对比

框架选型不是“谁功能最多”，而是“谁拥有状态、控制权和恢复语义”。

| 方案 | 适合场景 | 优势 | 本项目没有选择为主框架的原因 |
| --- | --- | --- | --- |
| 直接调用 OpenAI API | 极简调用或完全自定义协议 | 依赖少、控制最细 | 需要重写工具循环、结构化输出和模型适配，重复 SDK 已解决的问题 |
| OpenAI Agents SDK | 需要轻量 Agent、Tool Calling、结构化输出 | 原语少、可定制、不强制接管持久化 | 当前选择；外层仍需领域 Runtime |
| LangGraph | 动态 Graph、长任务、Checkpoint、Human-in-the-loop | 状态图和恢复能力完整 | 项目已有 Run/Checkpoint/Lease/Replay/Writer，引入后会出现两套状态机和事实源 |
| AutoGen | Group Chat、Selector、Swarm、开放式团队协作 | Multi-Agent 会话模式丰富 | 诊断流程需要固定职责、隔离上下文、Evidence 先落库，不需要自由发言或控制权转移 |
| CrewAI | 快速搭建 Role/Task/Crew/Flow | 高层抽象清晰、原型速度快 | 当前阶段少、并行规模小；高层封装会隐藏模型 request、工具 attempt 和预算边界 |
| LangChain | 大量模型、Retriever、Tool 和 RAG 集成 | 生态丰富、集成速度快 | 项目已有 provider-neutral Tool/Provider 层，暂无大规模 RAG 或第三方 integration catalog 需求 |
| MCP | 跨 Host 的 Tool/Resource 标准协议 | 互操作和动态发现 | 它不是 Agent 编排框架；当前九个本地工具不需要远程认证、发现和版本协商 |

## 8. 为什么没有选择 LangGraph

LangGraph 是最容易被面试官追问的替代方案。关键回答不是“LangGraph 太重”，而是**状态所有权冲突**。

DiagOps 已经实现：

- 版本化阶段顺序；
- Runtime Run/Attempt；
- Checkpoint 与 CAS；
- Lease 和 late-result fence；
- Token/tool/turn/deadline budget；
- SQLite 单 Writer；
- Resume、Replay、Diff 和 SSE event sequence。

如果只为了表达 Lead → Investigator → Critic 再引入 LangGraph，会出现：

```text
LangGraph checkpoint   vs DiagOps checkpoint
LangGraph state        vs Investigation/Runtime projection
LangGraph retry        vs Runtime retry/budget
LangGraph interrupt    vs cancellation/resume
LangGraph persistence  vs SQLite RuntimeStore
```

这会让崩溃恢复时无法明确哪一套状态才是真相。当前流程本质是固定阶段加最多三路并行，不需要第二个图运行时。

如果未来出现大量动态分支、人工中断点和跨进程图调度，并决定用 LangGraph**替换**现有 Runtime，而不是叠加，才值得重新评估。

## 9. 为什么没有选择 AutoGen 或 CrewAI

AutoGen、CrewAI 更适合用 Agent 角色和对话/任务抽象快速构建协作团队。DiagOps 的约束不同：

- Round 1 Investigator 必须互相隔离；
- Tool result 必须先持久化才能被引用；
- Critic 不能自由调用 Provider 工具；
- 每个角色和任务必须有明确 owner；
- 任何失败都要对应安全类别和恢复边界；
- 不允许 Group Chat 中的自然语言成为事实源。

因此项目保留 SDK 的模型执行能力，用 typed state 和 Evidence ledger 代替共享群聊。

如果产品变成低风险创意协作、客服分流或开放式研究，Group Chat/Swarm/Crew 模式才可能更合适。

## 10. 为什么 MCP 不是替代框架

MCP 解决的是 Host 如何发现并调用远程 Tool、Resource 和 Prompt；它不负责 Lead、Investigator、Critic 怎样协作，也不负责根因发布、预算和恢复。

当前工具都在同一后端进程中，并且工具清单固定。接入 MCP 会新增：

- Server identity 和认证；
- 工具 schema/description 的供应链信任；
- 远程 timeout、取消和重试；
- 动态工具列表和版本漂移；
- 跨租户数据与网络 egress。

在没有跨 Host 工具复用需求时，这些复杂度没有对应收益。未来出现多个独立工具服务或需要向 IDE/其它 Agent 暴露能力时，可以在 ToolRegistry 外增加 MCP adapter，但不替换 Runtime。

## 11. 什么时候应该重新考虑框架

| 需求变化 | 可重新评估的方案 |
| --- | --- |
| 动态图、频繁人工 interrupt、需要替换现有 Runtime | LangGraph |
| 自由 Group Chat、Swarm 或对话式团队协作 | AutoGen / CrewAI |
| 大规模 Retriever、文档 RAG 和第三方 Integration | LangChain |
| 跨 Host、跨语言复用工具与资源 | MCP |
| SDK 无法表达所需模型协议或工具循环 | 直接 OpenAI API |

框架应解决已经测量到的问题，而不是因为简历上多一个名字就引入。

## 12. 面试回答模板

### 30 秒版本

> 项目使用 OpenAI Agents SDK，但没有让 SDK 接管完整工作流。SDK 提供 Agent、Runner、FunctionTool 和结构化输出，负责单个角色的模型—工具循环；Lead、Investigator、Critic 的阶段调度、Evidence 持久化、预算、取消恢复和 Trace 由自研 Runtime 负责。这样既复用了 SDK 的通用能力，又保留了事故诊断所需的强状态和审计边界。

### 框架对比版本

> 没有选择 LangGraph，不是因为它能力不足，而是项目已有 Checkpoint、Lease、Replay 和 Writer，再叠加会形成两套状态机；没有选择 AutoGen/CrewAI，是因为事故诊断需要固定职责、隔离上下文和 Evidence 先落库，而不是自由 Group Chat；LangChain 更适合大量 RAG/集成，当前已有自己的 Tool/Provider 层；MCP 是工具互操作协议，当前九个本地工具还没有跨 Host 发现需求。
