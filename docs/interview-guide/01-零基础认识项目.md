# 01. 零基础认识项目

## 1. 先理解它解决的现实问题

想象一家电商的结算服务突然大量报错。工程师通常要做这些事：

1. 看告警发生时间和影响范围；
2. 查日志里有没有异常；
3. 看延迟、错误率、CPU 等指标；
4. 查事故前是否刚发布新版本；
5. 看上下游依赖是否超时；
6. 把线索按时间和因果关系串起来；
7. 提出根因候选、反证、下一步检查和修复建议。

人工做这些事很慢，而且容易因为经验偏见只盯着某一类数据。DiagOps 把这个调查过程产品化，但它不会直接修改生产系统。

项目名称可以拆成：

- **Diag**：Diagnosis，诊断；
- **Ops**：Operations，运维；
- **SRE**：Site Reliability Engineering，站点可靠性工程；
- **RCA**：Root Cause Analysis，根因分析。

## 2. 什么是 Agent

普通聊天模型像一个只能坐在房间里回答问题的人。Agent 则像一个被赋予以下东西的数字员工：

- 一份角色说明，例如“你是 Investigator”；
- 一个目标，例如“判断结算服务错误是否由数据库变慢导致”；
- 一组允许使用的工具，例如“查日志”“查 Trace”；
- 一个工作循环：思考下一步、调用工具、阅读结果、继续判断、输出结构化结论；
- 明确的边界：调用次数、时间、Token、数据范围和权限。

## 3. 什么是工具调用

LLM 本身看不到数据库、日志文件或 Prometheus。应用会把函数说明交给模型，例如：

```text
工具名：read_logs
用途：读取事故时间窗口内的日志证据
参数：开始时间、结束时间、关键词、级别、条数限制、查询原因
```

模型不会直接执行 Python。它只返回一个结构化请求，类似：

```json
{
  "start_time": "2026-08-24T01:00:00+08:00",
  "end_time": "2026-08-24T01:10:00+08:00",
  "reason": "确认错误是否从发布后开始",
  "keywords": ["timeout", "database"],
  "levels": ["ERROR"],
  "limit": 20
}
```

普通代码随后完成五件事：校验参数、检查权限和预算、调用真实 Provider、过滤与脱敏结果、把 Evidence ID 返回给模型。完整细节见 [工具调用与证据系统](04-工具调用与证据系统.md)。

## 4. 为什么要多个 Agent

一个模型从头做到尾有几个风险：

- 容易过早认定一个原因，之后只寻找支持它的证据；
- 同一上下文塞入太多信息，注意力会被稀释；
- 自己提出结论再自己审查，容易“既当运动员又当裁判”；
- 很难看清谁做了什么、哪一步失败。

V11 把职责拆成三类：

```text
Lead：决定最值得调查的问题
  ↓
Investigator：相互隔离地查证据、提候选
  ↓
Critic：专门寻找因果缺口和反证
  ↓
终态权威阶段：只发布 Critic 通过审查的候选
```

这不是简单让三个模型投票。多数意见仍可能一起出错，所以项目选择“角色分工 + 证据约束 + 明确裁决”，而不是“谁票多谁正确”。

## 5. 什么是“证据支持”

每一条有效证据都会保存为 `EvidenceItem`，包含：

- 唯一 Evidence ID；
- 来自日志、指标、Trace、发布还是其他 Provider；
- 时间；
- 摘要与有界结构化载荷；
- 数据对应的实体和时间范围；
- 来源与适配器版本；
- 属于哪一个 Runtime Run；
- 成功、部分成功还是失败。

Agent 不能只说“我认为数据库慢了”。它需要引用已经落库、属于本次运行、状态可用的证据 ID。项目在 [EvidenceItem](../../backend/domain/evidence.py) 和 [结果校验](../../backend/diagnosis/result_validation.py) 中机械检查这些引用。

## 6. 一次诊断的生活化比喻

可以把系统理解成一家医院：

| 项目概念 | 医院比喻 |
| --- | --- |
| Incident Event | 病人主诉和初始症状 |
| Lead | 主治医生，安排检查 |
| Investigator | 不同检查小组，但都能申请允许的检查 |
| Tool | 血检、影像、病历查询等标准检查入口 |
| Provider | 真正产生检查结果的设备或科室 |
| Evidence | 有编号、可追溯的检查报告 |
| Critic | 会诊专家，质疑“相关性是否真是因果” |
| Lead adjudication | 会诊结论发布关口；live 路径机械发布 Critic 接受项 |
| Validator | 医院系统检查报告是否完整、引用是否存在 |
| Runtime | 病历流转、超时、恢复、审计和状态管理系统 |

Validator 能判断“这份检查报告编号不存在”，但不应该替医生判断“这个影像一定说明肺炎”。这正是项目区分 Agent 推理与确定性代码的方式。

## 7. 项目做什么、不做什么

它做：

- 接收手工事件、Webhook、Alertmanager 告警和模拟事故；
- 收集只读证据；
- 生成多 Agent 调查计划、过程记录和根因候选；
- 输出报告、建议动作和验证建议；
- 记录人工审批和验证结果；
- 支持持久化运行、取消、恢复、重放、差异比较和实时事件流；
- 用 OpenRCA、RCAEval 和多层测试验证能力。

它明确不做：

- SSH 登录机器；
- 执行 Shell；
- 自动重启、扩容、回滚或修改配置；
- 让 Agent 自由访问任意 URL、文件路径或 PromQL；
- 把模型的隐藏思维过程持久化；
- 在证据不足时硬猜一个根因。

## 8. 最容易说错的三件事

### 错误一：“这是一个全自动修复系统”

不是。动作只是建议，`approved` 和 `done` 也只是人工记录的状态，不表示 DiagOps 执行了修复。

### 错误二：“多个 Agent 会投票选根因”

不是。Investigator 独立调查，Critic 做因果审查，终态权威阶段只发布通过审查的候选。当前 live 路径不会额外调用 Lead 模型重复判断。项目明确拒绝多数投票作为权威模型。

### 错误三：“现在默认启动就是完整 V11”

不是。仓库默认 `agents.enabled: false`，因此本地无密钥启动主要走兼容/确定性路径。V11 需要启用并配置受支持、通过能力认证的模型端点，而且正式效果评测尚未完成。

## 9. 学完本章的标准答案

如果面试官问“这个项目是什么”，可以答：

“它是一个面向应用服务故障的只读诊断平台。核心不是让 LLM 随意聊天，而是把事故调查拆成规划、取证、质疑和权威发布几个阶段。模型只能调用冻结的只读工具，每个结论必须引用持久化证据；普通代码负责权限、参数、预算、幂等、状态机和审计。当前 live 路径由 Critic 做最终语义审查，服务端只机械发布 accepted refs，不用规则替 Agent 猜根因。”
