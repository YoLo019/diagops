# 28. Agent 岗位简历亮点素材：DiagOps 后端项目

这份文档把 DiagOps 当前 V11 实现整理成 Agent 开发岗位可用的简历素材。它只写后端、Agent、Runtime、Tool、Evidence、安全和运行可靠性，不含前端内容。

## 项目一句话

DiagOps 是一个只读的 SRE 事故诊断后端：以持久化 Runtime 驱动 Lead、Investigator、Critic 多 Agent 协作，在预算内使用九个受控只读工具收集 Evidence，最终输出带证据引用、可恢复、可审计的根因候选。

## 50 条可选项目亮点

下面不是让你全部塞进一份简历。它是面试素材库：投递时通常选 4–6 条主亮点，面试追问时再展开对应编号。

## 推荐写进简历的亮点

### 最推荐的 5 条：投递 Agent 开发岗位

如果这些确实是你的主责内容，优先使用下面五条：前三条体现 Agent 设计，后两条体现工程化落地。

1. **Evidence-driven Multi-Agent Orchestration**：设计 Lead–Investigator–Critic 协作流程：Lead 拆解问题，Investigator 独立取证，Critic 审查反证；所有候选和最终结论都必须引用本次诊断已保存的 Evidence。
2. **Context Engineering**：使用 context projection、evidence digest 和 compact schema 为不同角色裁剪上下文，减少无关信息与 Token 消耗，降低 Agent 过早相互影响的风险。
3. **Tool Calling & Evidence Loop**：让 Agent 围绕信息缺口选择日志、指标、Trace、依赖等九个只读工具；通过 schema、scope、idempotency 和 deadline 校验，将结果持久化为 Evidence 后再进入推理。
4. **Agent Trace & Test Harness**：记录每次诊断的任务、模型调用、工具调用、Evidence、预算和失败事件；通过无需真实模型密钥的 Harness 覆盖超时、取消、重试和恢复等场景。
5. **Durable Agent Runtime**：基于 checkpoint、lease、idempotency 和并发控制保障长任务可恢复，处理超时、取消、重试、进程中断和 late result。

## 五条亮点的面试展开稿

下面每段都可以直接用于 1–2 分钟的项目介绍。先说加粗的结论，再按“怎么做 → 为什么这样做 → 出现异常怎么办”的顺序展开；不要把所有细节一次讲完，等面试官追问再继续。

### 1. Multi-Agent 协同诊断

“这个项目的核心不是让多个 Agent 自由讨论，而是把一次事故诊断拆成规划、取证和审查三个互相约束的职责。Lead 先根据告警和已有证据识别信息缺口，例如需要确认是发布变更、下游依赖还是单实例问题，再生成最多 3 个调查任务。每个 Investigator 都拥有独立任务、上下文和工具会话，可以并行收集证据，避免一个 Agent 的初步结论直接影响其他调查者。之后 Critic 不再自由查数据，而是对候选根因做时间关系、拓扑关系、作用机制、影响范围、症状与原因区分、反证和替代解释等因果检查；确实缺证时，最多只能发起一轮绑定审查结论的补充调查。最终只有通过 Critic 审查、且引用本次 Run 已持久化 Evidence ID 的候选才能发布。这样做的价值是把模型的语义判断保留给 Agent，同时用确定性规则约束证据和流程，避免‘多数 Agent 投票’或服务端凭规则替模型编造根因。”

追问“为什么不是日志、指标、发布三个固定 Specialist”时，回答：固定角色属于历史方案，容易把调查范围预先限制为数据模态；V11 的任务按信息缺口生成，多个 Investigator 使用相同的受控工具能力，但上下文彼此隔离，因此既保留调查多样性，也不扩大权限。

### 2. Context Engineering

“我没有把数据库对象或全部历史证据直接塞给模型，而是按角色构建最小上下文。Lead 只看事故描述和受控的初始证据，用来规划信息缺口；Investigator 只看自己任务需要的 incident、任务目标和 Evidence digest，不看其他 Investigator 的 Finding；Critic 只看候选、Finding、因果检查需要的证据引用闭包。Evidence digest 不是再让一个模型写摘要，而是服务端确定性地从完整证据账本中选择少量代表项：Round 1 默认只给 4 条起始证据，每类最多 2 条，并综合实体、信号族、变更分数和非指标锚点，避免 CPU、延迟一类高分指标挤掉日志、Trace 或网络证据。模型输出也使用紧凑的结构化契约，Task ID、Candidate ID、owner、预算等服务器拥有字段不让模型填写，Pydantic 会拒绝多余字段和越界值。这样既降低 Token 消耗和上下文噪声，也避免并行 Agent 因为共享中间结论而过早锚定。”

追问“压缩会不会丢信息”时，回答：完整 Evidence ledger 仍然持久化，digest 只是模型的起始可见窗口；Agent 发现缺口后仍可通过受控工具补证，Critic 也能围绕候选引用加载必要证据。

### 3. 受控 Tool Calling 与 Evidence 闭环

“Agent 不能执行 Shell、SSH、任意 SQL 或任意 PromQL，只能从注册表暴露的 9 个只读工具中选择，包括日志、指标、发布、服务目录、依赖、Trace、运行状态、告警和 verified memory。工具层分成 ToolSpec、ToolRegistry、ProviderRegistry 和 EvidenceItem：Agent 只看 provider-neutral 的名称和参数 Schema，具体的文件、Tempo、Prometheus 等执行细节留在 Provider 层。创建 Run 时会冻结有序工具 manifest，调用时再次检查工具是否仍对 Agent 可见、是否只读；服务端还会注入或校验事故时间窗、实体范围、依赖深度、枚举、条数、长度、预算和 deadline，避免 Agent 发出越权或过大的查询。每一次外部 I/O 前都会先持久化 running 的 ToolCallRecord，成功结果与 Evidence、Runtime Event 一起提交；只有已经提交的 Evidence ID 才能支撑 Finding 或候选根因。对于恢复或重试，系统用 query fingerprint 和 idempotency key 复用已成功的逻辑调用，并对 transport、rate-limit 等可分类瞬态失败做有界重试；成功调用却没有新增 Evidence 时会停止该 Investigator，避免无效循环。”

追问“为什么不直接把工具结果放在 prompt 里”时，回答：工具结果必须先进入带来源、范围、状态和所属 Run 的 Evidence ledger，之后才能被引用；这样报告、审计和失败分析都有同一份事实来源，也能区分可用证据与失败证据。

### 4. 持久化 Agent Runtime

“我把业务上的 Investigation 和一次可执行的诊断 Run 分开建模。Run 记录这次执行的版本、预算、deadline 和最终状态；Attempt 表示某个 worker 获得 lease 后的一次实际执行；Event 是按序持久化的运行事件；Checkpoint 保存每个已成功阶段的恢复位置和投影摘要。这样进程中断时，并不是从头再跑：系统只允许 interrupted Run 从最后一个已验证的完整 checkpoint 人工恢复，恢复会创建新的 Attempt，并继承原来的预算和绝对 deadline；已经成功提交的工具结果通过幂等键复用，不会再次访问外部系统。SQLite 写入由 RuntimeWriter 串行化，外部工具 I/O 仍可并行；lease owner 和 version 组成 execution fence，外部调用前后都会检查执行权，所以旧 worker、取消后或 deadline 后迟到返回的结果不能再提交。超时、取消、Provider 瞬态失败和模型输出错误都有明确状态、重试或失败语义，而不是把失败伪装成正常诊断结果。SSE 用数据库中持久化的事件序号做断线补齐，因此浏览器断线只影响订阅，不影响诊断本身。”

追问“为什么取消后不能直接恢复”时，回答：取消是用户明确终止的终态；只有 lease 过期等导致的 `interrupted` 才允许人工恢复，避免用户已经取消的任务被后台重新启动。

### 5. 诊断过程可观测性与测试

“一次诊断不是只保存最终报告。我会记录任务如何拆分、每次模型请求的 started/completed/failed 生命周期与 Token usage、每次工具调用的参数摘要和状态、产生的 Evidence、预算 reservation、阶段事件以及安全的失败分类。这样排查问题时可以回答‘哪个 Agent 在什么阶段、因为什么证据或失败停止’，而不是只能看一段最终自然语言。对外暴露和日志记录会做敏感字段脱敏，不直接返回原始异常、URL 或凭证。测试上，项目提供不依赖真实模型密钥的受控模型和 Provider 替身，用来稳定复现超时、取消、重试、服务重启、恢复和延迟返回等边界；真实模型评测与这类可靠性测试分开，未完成正式评测前不会把测试阈值写成准确率或上线效果。”

追问“为什么要区分可靠性测试和真实模型评测”时，回答：超时、并发、取消、幂等和迟到提交等系统语义需要可重复的确定性测试；根因正确率、成本和延迟则受模型和真实环境影响，必须通过单独的受控评测协议获得数据，不能用 mock 结果替代。

## 面试时的 30 秒版本

“我做的是一个只读的 SRE Multi-Agent 诊断后端。核心不是让多个模型自由聊天，而是由 Lead 拆解问题、隔离 Investigator 查证据、Critic 做因果和反证审查。模型只能调用九个只读工具，查询结果保存为可追溯证据后才能用于结论。我还记录每次诊断的模型、工具、证据和失败轨迹，并用无需真实模型密钥的验收 Harness 覆盖超时、取消、重试和恢复场景。”

基于 checkpoint、lease、idempotency 和并发控制保障长任务可恢复，正确处理超时、取消、重试、进程中断和延迟返回。
