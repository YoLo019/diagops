# DiagOps 可信度提升路线图(求职导向)

日期:2026-07-26
状态:草案(待按 AGENT.md 工作流登记审批后执行)

## 1. 背景与目标

本项目(DiagOps)作为求职作品集项目,当前已具备较强的工程地基:持久化
Agent 运行时(Lease/Fencing、Checkpoint、Replay、Run Diff)、证据契约与语义
校验、对抗性安全测试、1383 项自动化测试。

但在面试追问场景下,项目仍存在三个"玩具感"来源:

1. **假数据**:证据源以文件与 Mock 为主,从未诊断过真实环境故障。
2. **自编考题**:15-case 验收集为自建案例,缺少第三方标准基准的客观成绩。
3. **未完成的迭代**:V9 存在未修复的 blocker(OpenRCA 批次 evidence ID 冲突)。

**总目标**:把项目从"功能不少的玩具"升级为"规模有限的可信工程项目"。

**判断标准**:简历与口述中的每一条声明,都有一个面试官可亲自验证的工件
(artifact)支撑。可信度 = 声明数量 ÷ 每条声明的可验证性。

**非目标**:不追求真实用户、生产部署、分布式规模;不推翻现有架构;不新增
无评测跟进的"时髦功能"。

## 2. 第一阶段:可信度三步(最高优先级)

### ① OpenRCA 标准基准客观成绩

- 修复 V9 blocker:OpenRCA 确定性 Evidence ID 在 Fixed/Adaptive 配对调查中
  冲突,导致 Adaptive 证据阶段提交回滚。修复需要新 commit、新 Runtime
  数据库、新结果目录并重跑 batch-01。
- 跑完 OpenRCA 40-case Fixed vs Adaptive 配对评测并冻结工件。
- 产出:`predictions.json` + `summary.json` + `manifest`(含 SHA-256 完整性
  校验、git commit、模型、预算、成本记录);按故障类别的正确率;**失败案例
  分析报告**(哪些 case 错了、根因是什么)。
- 关键原则:有失败案例比全对更可信;每个数字可被评分脚本复现。

### ② 真实环境端到端演示

- 新增 `docker-compose.yml`,一条命令拉起:示例微服务 + Prometheus +
  Alertmanager + 本系统。
- 提供故障注入脚本(真实部署一个带 bug 的服务版本)。
- 告警经 webhook 打入 `POST /events`,系统从真实 Prometheus/日志拉取证据并
  产出报告。
- 产出:README 演示实录(告警时间 → 调查 ID → 报告截图,证据链可点开);
  面试官可在 15 分钟内在自己机器上复现完整链路。

### ③ MCP 工具暴露

- 将现有受限只读诊断工具(`read_logs`、`query_metrics`、`query_prometheus`
  等)以 MCP server 形式暴露。
- 验收标准:一个**未修改过的第三方 MCP 客户端**(如 MCP Inspector /
  Claude Desktop)能直接列出并成功调用工具——证明工具契约是真实的。
- 产出:README 配置方法与调用截图。

### 卫生项(随第一阶段一并完成)

- GitHub Actions CI:ruff + 全量 pytest 每次提交自动运行,挂 badge。
- README 按"15 分钟复现"标准重写:架构图、基准数字、Limitations 章节
  置于第一屏。
- 整理已有 spec / plan / 验收记录为 ADR 目录并链接进 README。

## 3. 第二阶段:诊断深度

### ④ Trace(调用链)证据

- 新增只读 Jaeger/Tempo Provider,将"请求经过哪些服务、哪一跳变慢/报错"
  纳入证据体系,走同一套证据契约与语义校验。
- 补全微服务可观测性三支柱(logs / metrics / traces),解锁跨服务故障
  传播分析。

### ⑤ 代码 diff 作为受控证据

- 新增只读 CodeProvider,将"故障版本与上一稳定版本之间的 git diff"作为
  新证据类型接入,走既有证据 ID 引用与校验机制。
- 诊断粒度从"故障类型级"向"代码级"迈进一步,同时保持只读安全边界
  (不允许 Agent 执行任意代码)。

## 4. 第三阶段:工程文化与自我改进

### ⑥ 评测回归与多模型对比

- 将 OpenRCA 评测固化为回归门禁:每次修改 prompt、模型、校验逻辑时自动
  重跑并对比,防止静默退化。
- 完成 DeepSeek 独立 Gate,产出多模型对比表(GPT vs DeepSeek 的正确率 /
  成本 / 延迟)。

### ⑦ 带防退化闸门的自进化 skill

- 前置依赖:⑥ 的评测回归必须先就位,否则"进化"不可验证、不做。
- 形态:系统从诊断失败案例中提炼新的诊断规则/skill 候选 → 自动在冻结
  基准上回归验证 → 通过才入库,不通过则丢弃,全程保留审计记录。
- 定位:不是"LLM 自由发挥",而是"带客观验收闸门的自我改进机制",与
  项目证据驱动哲学一致。

## 5. 全程原则

1. 每一步独立可停,完成后项目都处于可展示状态。
2. 每个新功能必须带着对应的测试与评测一起落地;无证据跟进的功能宁可
   不做。
3. 严守 AGENT.md 生产安全边界:全程只读,建议不等于执行,不新增自动
   修复能力。
4. 按仓库工作流,各阶段启动前在 `docs/superpowers/current.md` 登记迭代并
   完成 spec / plan 审批。

## 6. 表述边界(完成后仍需注意)

- 诊断智能仍以简单规则为兜底,不声称规则层"聪明";其定位是可靠基线,
  智能主体是经验证契约约束的模型层。
- 不声称拥有真实用户或生产部署;展示的是"为真实使用做过的工程准备"。
- 基准成绩如实报告,包含失败案例;不复现不出的数字不进 README。
