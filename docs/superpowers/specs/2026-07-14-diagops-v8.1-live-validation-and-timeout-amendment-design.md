# DiagOps V8.1 Live Validation And Timeout Amendment

Status: `approved`

This focused amendment extends the approved V8.1 reliability and Provider
compatibility design. All original V8.1 requirements remain authoritative
unless this document explicitly narrows or extends them.

## 1. Context

The Task 5 OpenAI diagnostic run
`v8-1-diagnostic-20260714T030835344662Z-1043e2b4` completed with five clean
rows and no PASS claim. It exposed two gaps:

1. `single_bad_instance` reached the post-runtime contract validator, raised a
   `ValueError`, and was projected as `unknown`. The safe artifact cannot tell
   whether the task, execution, finding, review, semantic-reference, or final
   run-status contract failed.
2. The configured overall timeout was 60 seconds, but two cases took about 120
   seconds and one case took about 832 seconds. `asyncio.wait_for` requested
   cancellation but waited for SDK/network cleanup, so it did not enforce a
   useful wall-clock bound on the live path.

The diagnostic therefore triggered the existing Task 5 stop gate. The
canonical OpenAI gate and all Provider compatibility work remain blocked.

## 2. Goal

Make every post-runtime validation rejection safely classifiable and bound the
OpenAI network path closely enough that a diagnostic case cannot remain inside
the SDK's default transport timeout or retry window.

Success requires:

1. No post-runtime validation failure is persisted or written to a reliability
   artifact as `unknown` when its validation boundary is known.
2. The configured runtime timeout remains the outer budget, while the OpenAI
   transport timeout expires earlier and performs no client-level automatic
   retry.
3. Timeout or validation failure preserves deterministic RCA and one complete,
   attributable, structured Agent failure result.
4. No exception message, prompt, response, reasoning, credential, URL, or raw
   Provider payload enters persistence, API output, UI output, or artifacts.

## 3. Scope

### 3.1 In Scope

1. Add safe post-runtime validation categories.
2. Persist and expose the category as an additive Agent execution field.
3. Add one explicit result-validation execution step and stabilization
   category.
4. Preserve OpenAI Provider/model attribution on validation fallback.
5. Construct the existing OpenAI Responses model with a project-owned
   `AsyncOpenAI` client that has an explicit transport timeout and no automatic
   retry.
6. Keep `asyncio.wait_for` as the overall runtime deadline.
7. Add deterministic tests and rerun the five-case OpenAI diagnostic.

### 3.2 Non-Goals

1. Do not change prompts, arbitration, evidence rules, reliability thresholds,
   or expected causes.
2. Do not accept, repair, or reinterpret invalid model output.
3. Do not add a subprocess runtime, queue, worker service, retry wrapper,
   Provider fallback, or arbitrary Base URL.
4. Do not switch the OpenAI path from the Responses API to Chat Completions.
5. Do not begin DeepSeek or Task 6 work under this amendment.
6. Do not change production systems or add mutation tools.

## 4. Validation Contract

### 4.1 Safe Category Enum

Add `ResultValidationCategory` with these frozen values:

```text
task_contract
execution_contract
finding_contract
finding_revision_contract
review_attribution
review_contract
semantic_reference
run_status_contract
```

The enum identifies only the validation boundary. It must never contain model
text, an exception message, an evidence value, or another dynamic string.

### 4.2 Additive Domain Fields

Add these contract values:

1. `ExecutionStepKind.RESULT_VALIDATION = "result_validation"`.
2. `StabilizationCategory.RESULT_VALIDATION = "result_validation"`.
3. `AgentExecution.result_validation_category:
   ResultValidationCategory | None = None`.

Existing payloads remain readable because the new execution field is optional.
Agent executions are persisted as JSON payloads, so this amendment does not add
a SQLite table, column, schema version, or migration.

API and frontend types receive the same additive enum and optional field. The
UI may show a compact safe category label; it must not show `error_message` for
SDK executions.

### 4.3 Structured Validation Error

The orchestrator uses one internal `AgentResultValidationError` carrying only a
`ResultValidationCategory`. Each validation boundary converts Pydantic errors,
reference errors, and explicit contract failures at that boundary into the
corresponding category.

The validator remains fail-closed. Replacing a generic `ValueError` with a
structured error changes observability only; it does not make any previously
invalid result valid.

### 4.4 Failure Projection

When post-runtime validation fails, the orchestrator replaces the rejected SDK
result with one deterministic fallback result containing:

1. One failed `result_validation` task/execution.
2. `failure_category=invalid_reference` only for `semantic_reference`;
   otherwise `failure_category=invalid_output`.
3. The exact safe `result_validation_category`.
4. `primary_stabilization_category=result_validation`.
5. The selected OpenAI Provider and model attribution copied from the rejected
   run summary or the runtime configuration.
6. No findings or review from the rejected result.

The replacement result must pass the normal V7 result validator before atomic
persistence. If replacement validation or persistence fails, the existing
safe persistence-recovery behavior remains authoritative.

## 5. Timeout Contract

### 5.1 Two-Layer Budget

`DIAGOPS_AGENTS_TIMEOUT_SECONDS` remains the overall runtime budget.

For the OpenAI path:

1. Build the existing `OpenAIResponsesModel` with a project-owned
   `AsyncOpenAI` client.
2. Set the client's transport timeout to
   `max(1 second, overall_timeout - 5 seconds)`.
3. Set `max_retries=0`; retries outside the overall budget are forbidden.
4. Keep `asyncio.wait_for(..., timeout=overall_timeout)` around the complete
   multi-agent run.
5. Close the client after the run, including timeout, cancellation, and error
   paths.

For configured budgets of five seconds or less, the transport and overall
timeout may be equal. Unit tests that inject a turn callable remain independent
of the real client and may use sub-second overall timeouts.

### 5.2 Ownership

One helper owns OpenAI Responses model/client construction. It accepts only the
explicit model name and timeout budget. It does not accept a Base URL, key
value, retry count, or arbitrary client options.

The key remains in the local process environment and is read by the OpenAI
client. It is never returned from the helper or retained in settings, logs,
artifacts, source, or YAML.

The application container and V8.1 live runner use this same helper. There is
still one Agents SDK runtime and one OpenAI transport path.

### 5.3 Timeout Semantics

The outer deadline remains the authoritative run status. A timeout records:

```text
failure_category=timeout
primary_stabilization_category=cancelled_or_timeout
```

Any findings completed before timeout may remain visible as partial diagnostic
context, but no review is accepted after timeout. A timed-out request must not
be detached as a background paid request.

This amendment deliberately does not claim process-kill precision. It requires
the async OpenAI transport itself to expire before the outer budget so normal
SDK cancellation and cleanup have bounded time to finish.

## 6. Artifact Contract

Schema-v3 remains the current artifact version. Add
`result_validation_category` to the allowlisted execution projection. The
field is `null` for non-validation steps and one frozen enum value for a result
validation failure.

Diagnostic rows continue to include only structured categories. Historical
schema-v1/v2 files and existing schema-v3 artifacts remain immutable and
readable.

## 7. Compatibility And Rollout

1. Domain, persistence, API, frontend, and artifact changes are additive.
2. Old execution payloads default `result_validation_category` to `None`.
3. No SQLite migration is required.
4. OpenAI remains the only live Provider touched by this amendment.
5. The later DeepSeek adapter must retain its separately approved fixed client
   and capability contract; it does not reuse OpenAI credentials or endpoint
   configuration.
6. The canonical gate remains unchanged and blocked until the amended
   diagnostic passes its stop gate.

## 8. Test Strategy

Use TDD for every behavior change.

### 8.1 Validation Tests

1. Force each of the eight validation boundaries to fail and assert the exact
   safe category.
2. Assert the rejected findings/review are not persisted.
3. Assert memory and SQLite round-trip the new optional execution field.
4. Assert old payloads without the field still load.
5. Assert API, frontend types, and schema-v3 projection preserve the enum while
   excluding raw exception and model text.

### 8.2 Timeout Tests

1. Assert the OpenAI helper creates an `OpenAIResponsesModel`, preserves the
   exact model name, uses the derived transport timeout, and sets zero retries.
2. Assert missing credentials still produce a visible skipped run without
   constructing a paid client.
3. Assert the outer timeout preserves already completed findings and records
   the current execution step, round, and attempt.
4. Assert client cleanup runs on success, timeout, cancellation, and transport
   failure.
5. Assert timeout paths contain no credential or endpoint value.

### 8.3 Live Stop Gate

After all key-free checks pass, rerun only:

```powershell
uv run python -m backend.services.v7_live_acceptance --mode live --runs-per-case 1
```

Continue to the unchanged canonical OpenAI gate only when:

1. Exactly five clean rows are present.
2. No row has `unknown` stabilization or failure classification.
3. Every failed validation row has an exact result-validation category.
4. Every timeout row is structurally complete and attributable.
5. Case durations demonstrate that the 832-second transport-window regression
   is no longer present.

Any new prompt, mapping, arbitration, or output-contract defect requires a
separate amendment. Thresholds must not be lowered.

## 9. Operational Verification Limitation

The design was checked against the installed `openai-agents 0.18.1` and
`openai 2.45.0` interfaces. They expose `OpenAIResponsesModel(model,
openai_client)` and `AsyncOpenAI(timeout=..., max_retries=...)`.

The OpenAI Developer Docs MCP was unavailable in the current Codex session, and
the local CLI installation attempt was denied by Windows. Official documentation
must be rechecked before implementation if the MCP becomes available. A docs
lookup must not broaden this amendment or silently change the installed SDK
version.

## 10. Acceptance Criteria

This amendment is complete only when:

1. All eight validation categories have focused RED/GREEN tests.
2. No known validation boundary produces `unknown`.
3. OpenAI Responses client construction has an explicit bounded timeout and no
   automatic retries.
4. Memory, SQLite, API, frontend, artifact, and old-payload checks pass.
5. Full Ruff, pytest, frontend build, and diff checks pass.
6. The five-case live diagnostic passes the amended stop gate.
7. The unchanged canonical OpenAI gate passes before Task 6 begins.
