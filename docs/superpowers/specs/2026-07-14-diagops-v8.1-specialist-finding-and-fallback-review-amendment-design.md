# DiagOps V8.1 Specialist Finding And Fallback Review Amendment

Status: `approved`

This focused amendment extends the approved V8.1 reliability specification and
the live-validation amendment. Their requirements remain authoritative unless
this document explicitly changes them.

## 1. Context

The amended five-case OpenAI diagnostic
`v8-1-diagnostic-20260714T040514662658Z-19a2f22f` completed every network path
inside the configured timeout. Three cases produced a real review, while
`single_bad_instance` and `traffic_spike` safely fell back with:

```text
failure_category=invalid_output
result_validation_category=review_contract
primary_stabilization_category=result_validation
```

The artifact contains no prompt, raw response, reasoning, or free-text model
payload. A key-free local reproduction established the failing contract path:

1. A Specialist may validly return an evidence-backed `signal` or an
   evidence-free `gap`.
2. When no active Specialist finding supports or contradicts a root-cause
   candidate, `build_hybrid_coordination_review` intentionally seeds candidates
   from deterministic hypotheses and assigns `decision_status=fallback`.
3. The post-runtime validator currently requires every accepted review cohort
   to contain at least one candidate with a Specialist finding reference.
4. It therefore rejects the builder's valid deterministic fallback review as
   `review_contract`.

The installed structured output schema exposes all `AgentFindingType` enum
values, but the Specialist instructions do not define when to choose
`root_cause`, `contradiction`, `signal`, or `gap`. Consequently, a model can
classify strong causal evidence as a non-conclusive `signal` without violating
the transport schema. The previous `traffic_spike` diagnostic succeeded while
the amended diagnostic followed the fallback path, which is consistent with
this under-specified semantic choice.

This is a prompt and arbitration-contract defect. The previous live-validation
amendment explicitly prohibited prompt and arbitration changes and required a
stop when such a defect appeared. This document provides the required approval
boundary for the narrow correction.

## 2. Goal

Make Specialist finding classification explicit and make the post-runtime
validator agree with the project-owned fallback review builder, without
inventing root causes, weakening evidence checks, repairing model output, or
changing the canonical reliability thresholds.

## 3. Scope

This amendment changes only:

1. Specialist finding-type instructions and structured schema descriptions.
2. The review validator rule for a code-owned deterministic fallback review.
3. Focused runtime, orchestration, and acceptance tests for these paths.
4. The five-case diagnostic and unchanged canonical OpenAI gate sequence.

## 4. Non-Goals

This amendment does not:

1. Change expected causes, deterministic RCA ranking, evidence-to-cause rules,
   or reliability thresholds.
2. Force a Specialist to agree with the deterministic baseline.
3. Promote a `signal` or `gap` into a root-cause finding in application code.
4. Add retries, JSON repair, output extraction heuristics, or another Agent
   round.
5. Persist prompts, raw model responses, reasoning, validation predicates, or
   free-text exception details.
6. Change Provider selection, add DeepSeek, or alter the OpenAI Responses API.
7. Treat a deterministic fallback review as a real Agent review.

## 5. Specialist Finding Contract

The Specialist instructions and structured output schema must define these
semantics consistently:

| Finding type | Required meaning |
| --- | --- |
| `root_cause` | Supplied evidence directly supports the named `related_cause_type`; at least one supplied evidence ID is required. |
| `contradiction` | Supplied evidence directly contradicts the named `related_cause_type`; at least one supplied evidence ID is required. |
| `signal` | Supplied evidence is relevant but does not support a root-cause or contradiction claim; at least one supplied evidence ID is required. |
| `gap` | Supplied evidence is absent or insufficient for a diagnostic claim; evidence IDs may be empty and unsupported cause attribution must not be invented. |

Additional rules:

1. The model chooses the finding type from supplied evidence, not from a demand
   to match the expected test cause.
2. A `root_cause` or `contradiction` without a cause type or evidence remains
   invalid.
3. A `signal` never counts as root-cause support, regardless of confidence.
4. A `gap` never counts as evidence and must not be promoted by code.
5. All evidence IDs remain restricted to the selected Specialist's allowlist.
6. Round-two revision, conflict selection, and deterministic decision ownership
   remain unchanged.

The instruction text must be concise and provider-neutral so the same
project-owned semantic contract can be reused by the later DeepSeek adapter.

## 6. Fallback Review Contract

The post-runtime validator may accept a candidate cohort without Specialist
finding references only when every condition below holds:

1. `review.decision_status == fallback`.
2. `review` is exactly reproducible by `build_hybrid_coordination_review` from
   the validated findings, evidence, hypotheses, run status, and attribution.
3. Every candidate contains at least one valid supporting or contradicting
   evidence ID from the investigation.
4. Every candidate cause and evidence reference matches the deterministic
   hypotheses used by the builder.
5. The review and run summary retain the selected Provider and model.

For `agreement`, `conflict`, or `agent_leads`, at least one candidate must still
contain a valid supporting or contradicting Specialist finding reference.
Existing semantic-reference validation remains mandatory for every referenced
finding and evidence ID.

An accepted fallback review is projected as:

```text
real_review=false
fallback=true
decision=fallback
valid_result=true
```

It does not contribute to the canonical `>=14/15 real Agent reviews` threshold.
The change removes a false `review_contract` classification; it does not turn
insufficient Agent support into acceptance credit.

## 7. Runtime And Data Flow

The runtime remains one OpenAI Agents SDK graph:

```text
validated evidence
  -> Specialist receives explicit finding-type semantics
  -> local Pydantic and evidence-allowlist validation
  -> code-owned hybrid review builder
  -> post-runtime structural and semantic validation
  -> atomic SDK result persistence or deterministic fallback
```

No new persisted field or schema migration is required. Existing
`ResultValidationCategory`, `FailureCategory`, `StabilizationCategory`, API,
frontend, and schema-v3 artifact shapes remain unchanged.

## 8. Failure And Safety Behavior

1. Invalid JSON, invalid enum values, missing required evidence, out-of-allowlist
   references, attribution mismatches, and non-fallback candidates without
   finding support remain fail-closed.
2. A valid signal/gap-only result becomes a visible deterministic fallback, not
   `review_contract` and not a real review.
3. Prompt clarification must never contain expected acceptance causes or tell a
   Specialist to produce `root_cause` unconditionally.
4. The runtime must not retry solely to obtain a preferred finding type.
5. Tracing payload rules, redaction, timeout, client lifecycle, and no-mutation
   production safety boundaries remain unchanged.

## 9. Test Strategy

Implementation must use TDD and observe each focused regression test fail before
production edits.

Required automated coverage:

1. A signal/gap-only Specialist result reproduces the current
   `review_contract` failure before the fix and becomes a valid fallback after
   the fix.
2. The accepted fallback remains `real_review=false`, retains valid references,
   and receives no expected-candidate credit.
3. An evidence-backed root-cause finding still produces a real review with
   finding and evidence references.
4. Agreement, conflict, or agent-leads reviews without Specialist finding
   support remain rejected as `review_contract`.
5. Unknown evidence IDs and mismatched finding IDs remain rejected.
6. Specialist instruction and output schema tests assert the four finding-type
   semantics without embedding expected incident causes.
7. Existing timeout, result-validation, redaction, persistence, artifact, and
   frontend contract suites remain green.

## 10. Live Verification And Stop Gates

After focused and full automated verification:

1. Run the five-case OpenAI diagnostic with one repetition per case.
2. Inspect only allowlisted structured fields.
3. Stop if a row is `unknown`, exceeds the timeout contract, leaks sensitive
   data, or exposes another unapproved prompt/mapping/arbitration defect.
4. A classified fallback is safe but does not prove reliability. If more than
   one of five diagnostic rows is not a real review, stop and reassess before
   paying for the canonical gate because the `>=14/15` threshold is unlikely to
   pass.
5. If the diagnostic is acceptable, run the unchanged 15-row canonical OpenAI
   gate.
6. Do not lower thresholds or count fallback rows as real reviews.

The tracing-client regional 403 is non-fatal telemetry behavior and is not an
acceptance failure. This amendment does not change OpenAI tracing behavior.

## 11. Acceptance Criteria

This amendment is complete only when:

1. The signal/gap-only regression is a valid, evidence-safe fallback rather than
   `review_contract`.
2. Strong evidence can produce an explicitly specified root-cause finding path
   without code-side promotion or forced agreement.
3. Non-fallback reviews still require valid Specialist finding support.
4. Focused tests, the full backend suite, Ruff, frontend build when affected,
   `git diff --check`, redaction scans, and artifact allowlist checks pass.
5. The five-case diagnostic satisfies its stop gate.
6. The unchanged canonical OpenAI gate passes before the original V8.1 Task 6
   begins.

## 12. Resolved Risks

1. **Risk: prompt wording inflates agreement.** Resolution: define semantic
   choices without exposing expected causes or requiring baseline agreement.
2. **Risk: validator relaxation accepts unsupported conclusions.** Resolution:
   relax only the code-owned `fallback` path; all conclusive decisions retain
   the finding-reference requirement.
3. **Risk: fallback is counted as success.** Resolution: preserve
   `real_review=false` and all canonical thresholds.
4. **Risk: another Provider receives different semantics.** Resolution: keep
   the instruction contract provider-neutral and reuse it in the planned
   DeepSeek adapter.
