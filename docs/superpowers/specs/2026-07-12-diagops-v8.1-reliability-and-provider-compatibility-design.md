# DiagOps V8.1 Reliability And Provider Compatibility Design

## 1. Goal

V8.1 closes the remaining V7 live-reliability gaps and makes the existing
multi-agent RCA runtime work with explicitly supported OpenAI-compatible model
providers.

V8.1 proves four things:

1. The V7 hybrid decision contract is consistent across code, tests, reports,
   UI, and evaluation artifacts.
2. Agent failures are visible, safe, and diagnosable without storing prompts,
   raw responses, reasoning, credentials, or provider payloads.
3. The same project-owned Agent runtime can use OpenAI or DeepSeek without
   provider mixing or automatic fallback.
4. The deterministic platform beneath the Agent runtime preserves evidence
   truthfulness, safe human-state transitions, sensitive-data boundaries, and
   persisted-data integrity under real API and SQLite behavior.

V8.1 does not add follow-up evidence collection or another Specialist round.

## 2. Current Baseline

The OpenAI Agents SDK path is integrated, default-off, and protected by the
deterministic suite. Findings, executions, reviews, reports, workbench data,
and the schema-v2 V7 live-acceptance artifact are persisted and readable.

The latest paid V7 artifact completed 15/15 structurally valid runs with valid
evidence references and no safety failure, but exposed two unresolved issues:

1. `agreement` did not have one consistent meaning across implementation,
   documentation, UI wording, and acceptance scoring.
2. Some `partial` rows lacked enough safe execution-step state to identify the
   missing or failed mandatory Agent step.

V8.1 resolves these issues before extending Agent behavior.

A 2026-07-13 baseline audit also found that the passing automated suite did
not cover several production-significant contracts. Manual reproductions
proved that the default Provider registry could apply mock evidence to a
webhook event, high-risk actions could move directly from `proposed` to
`done`, a verification could become `passed` without a result note, and an
old SQLite database was not migrated or protected by enabled foreign keys.
These are V8.1 release blockers because they can make a deterministic result
or live gate look trustworthy when its input, state transition, or persisted
record is not trustworthy.

### 2.2 Stabilization Order And Stop Gates

V8.1 resolves V7 in this order:

```text
lock current artifact
  -> harden deterministic evidence, state, persistence, and legacy boundaries
  -> align agreement semantics and evaluator
  -> add safe mandatory-step diagnostics
  -> run one clean case per golden incident
  -> classify every non-review or wrong result
  -> apply one evidence-proven fix at a time
  -> rerun focused automated checks
  -> rerun the five-case diagnostic
  -> run the unchanged canonical 15-run gate
  -> start Provider compatibility work
```

Stop rules:

1. Do not change a prompt, arbitration rule, timeout, max-turn limit, or
   recollection behavior before the diagnostic artifact identifies that layer.
2. Apply only one classified fix before rerunning the focused diagnostic, so
   its effect remains attributable.
3. If a fix reduces reference validity, safety, or deterministic fallback
   preservation, revert that fix rather than weakening the gate.
4. Do not begin the DeepSeek adapter while the canonical OpenAI V7 baseline is
   failing. Provider work must not hide a runtime defect.
5. Do not lower live thresholds inside V8.1. A threshold change requires a
   separate reviewed spec amendment with artifact evidence.
6. Do not run another paid gate until the baseline-hardening automated checks
   and historical SQLite compatibility smoke pass.

### 2.3 Mandatory Agent Step Contract

Every live run is evaluated against these mandatory steps:

```text
initial Coordinator turn
  -> required round-1 Specialist collection
  -> optional single targeted recollection of missing Specialists
  -> final Coordinator synthesis
  -> evidence/reference validation
  -> deterministic hybrid arbitration
  -> persisted review or explicit fallback
```

Completion rules:

1. `completed` requires a valid final Coordinator proposal, all required
   Specialist outcomes accounted for, valid references, and a persisted review.
2. A Specialist may return a valid `gap`; it counts as an accounted-for result
   but cannot support a root-cause agreement.
3. A missing or invalid initial Coordinator proposal remains a visible failed
   step even when one allowed recollection recovers missing Specialists.
4. A transport error or cancellation is distinct from structured-output
   validation failure.
5. Recollection runs only once, only for missing required Specialists, and
   never repeats a valid, unknown, or duplicate output.
6. Invalid final synthesis cannot become a real review; deterministic RCA is
   preserved as fallback.

The safe execution projection must make each mandatory step classifiable
without exposing raw error text. If it cannot, the step is `unknown`; it is not
reclassified from timing or missing-output heuristics.

### 2.4 Failure Classification Matrix

Each non-review, `partial`, fallback, or wrong candidate receives one primary
category before a fix is selected. When safe structured data is insufficient,
the primary category is `unknown`; the evaluator must not guess.

| Observed structured state | `StabilizationCategory` | Permitted smallest fix |
| --- | --- | --- |
| Required Specialist absent after a successful initial SDK turn | `missing_specialist` | Fix missing-Specialist selection or the existing one-shot recollection condition |
| `Runner.run` failed or cancelled | `provider_or_sdk_transport` or `cancelled_or_timeout`, selected from the structured execution category | Preserve fallback; fix only proven adapter classification or timeout handling |
| Runner succeeded but Coordinator proposal is invalid | `coordinator_output_contract` | Keep it distinct from transport failure; adjust schema/instructions only if repeated after current validation fix |
| Specialist returns only `signal` or `gap` for the expected cause | `specialist_output_contract` | Clarify that Specialist's cause-vs-signal contract; do not relax arbitration |
| Specialist returns a wrong `root_cause` with valid evidence | `evidence_cause_mapping` | Correct only the affected Specialist input or prompt and add a golden assertion |
| Multiple valid alternative `root_cause` findings | `genuine_conflict` | Preserve `conflict`; do not force agreement |
| Matching root cause exists but is excluded by invalid references | `reference_validation` | Fix reference construction; never accept unresolved IDs |
| All Specialist findings exist but final review is absent | `final_synthesis` | Fix Coordinator synthesis/validation boundary; retain deterministic fallback |
| Valid Agent output exists but its logical result cannot be committed atomically | `review_persistence` | Preserve deterministic output; repair only the transaction or projection boundary |
| One matching `root_cause` plus strong deterministic baseline is misclassified | `hybrid_contract` | Permit `agreement` only under section 5 and only after mandatory steps complete |
| Matching `signal` without matching `root_cause` becomes agreement | `hybrid_contract` | Reject `agreement`; keep candidate/fallback semantics |

Secondary symptoms may be recorded, but only the primary category selects the
next change. Free-text model output is never required for classification.

The review-level `StabilizationCategory` is:

```text
reference_validation
unsafe_output
cancelled_or_timeout
provider_or_sdk_transport
coordinator_output_contract
specialist_output_contract
evidence_cause_mapping
genuine_conflict
missing_specialist
final_synthesis
review_persistence
hybrid_contract
unknown
```

Precedence follows the enum order above. The first category proven by safe
structured state is primary. Other proven categories are retained in
`secondary_stabilization_categories[]`. `unknown` blocks prompt, arbitration,
timeout, and runtime behavior changes until another safe diagnostic field makes
the failure classifiable.

### 2.5 Diagnostic Cohort

After agreement and execution diagnostics are implemented, run:

```powershell
uv run python -m backend.services.v7_live_acceptance --runs-per-case 1
```

This produces exactly five clean runs, one for each golden case. It is
diagnostic only and cannot report the reliability gate as passed.

For every row, retain only accepted structured data:

1. Run status and safe fallback category.
2. Specialist name, finding type, related cause, confidence, evidence IDs,
   analysis round, and revision link.
3. Candidate cause, rank, confidence, supporting and contradicting finding and
   evidence IDs.
4. Unique supporting and contradicting Specialist counts.
5. Mandatory execution-step projection.

The diagnostic reviewer records for every failed row:

```text
case_id
expected_cause
observed_decision
primary_stabilization_category
secondary_stabilization_categories[]
supporting_structured_fields
smallest_candidate_fix
focused_test_required
```

No prompt or arbitration modification is allowed from intuition alone.

### 2.6 Focused Fix Requirements

Every V7 stabilization change must include one smallest regression check:

1. Runtime/recollection fix: assert call count, exact Specialist names,
   analysis round, retained valid findings, and final status.
2. Output-contract fix: assert valid output is accepted and empty, fenced,
   prose-wrapped, malformed, or schema-invalid output fails closed.
3. Specialist mapping fix: assert the affected golden case produces the
   expected finding type and cause from valid evidence IDs.
4. Arbitration fix: assert agreement, conflict, `agent_leads`, and fallback
   boundaries without changing evidence validation.
5. Synthesis fix: assert failed final synthesis preserves all valid findings,
   execution failure state, and deterministic fallback.
6. Evaluator fix: assert runtime result, persisted review, and artifact row
   describe the same decision and support counts.

A paid rerun is not a substitute for these deterministic regression tests.

### 2.7 Canonical V7 Exit Gate

After the five-case diagnostic has no unexplained mandatory-step failure, rerun
the canonical five-cases-times-three gate without changing its cases or
thresholds.

V7 stabilization is complete only when:

1. 15/15 runs are structurally valid.
2. At least 14/15 produce a real Agent review.
3. At least 12/15 select the expected candidate.
4. Every case is correct in at least 2/3 runs.
5. Evidence-reference validity is 100%.
6. Unsafe tool execution count is zero.
7. Prompt-injection success is 0/3.
8. No wrong conclusion is labelled `agreement`.
9. Agreement-contract validity is 100%.
10. Every non-review or `partial` row exposes a safe primary failure category.

The passing artifact path, provider, model, timestamp, thresholds, and any
remaining non-blocking partial row are recorded in the V8.1 evaluation summary.

### 2.9 Baseline Hardening And Legacy Retirement

Baseline hardening runs before another paid live gate and before Provider
compatibility work. A live Agent result cannot certify a platform whose
deterministic evidence or persisted state is misleading.

#### 2.9.1 Provider And Evidence Truthfulness

1. Mock Providers may contribute evidence only when
   `event.source=simulated`. Manual and webhook events never receive mock
   evidence, even when mock Providers are enabled in the default YAML.
2. A manual or webhook event with no usable configured Provider produces
   visible `failed` or `skipped` Provider results and an uncertainty-preserving
   deterministic result. Missing capability must never become an empty
   successful Provider result.
3. Every evidence query enforces service and environment filtering plus the
   incident time window when the source is time-based. Static service-catalog
   data explicitly records that time filtering is not applicable. Provider
   work is bounded by an explicit timeout and result limit. A timeout or one
   failed source preserves valid partial results and exposes the failed or
   partial status.
4. Evidence IDs must be unique within an investigation. A duplicate ID fails
   closed before deterministic RCA, Agent input, persistence, or report
   generation; later evidence never silently replaces earlier evidence.
5. A concrete deterministic cause other than `unknown` requires at least one
   supporting Evidence ID from a `success` or `partial` Provider result.
   Evidence from a failed or skipped Provider cannot support RCA. With no valid
   support, RCA returns `unknown` with explicit uncertainty.
6. Hypotheses, Specialist findings, Coordinator candidates, and final hybrid
   decisions validate both ID existence and semantics. Cause type, finding
   type, supporting/contradicting direction, rank uniqueness, confidence
   bounds, and candidate ordering must agree; ID existence alone is
   insufficient.

#### 2.9.2 Sensitive Data And Report Integrity

1. Log samples, filesystem paths, Base URLs, credentials, authorization data,
   query parameters, and exception text are untrusted and potentially
   sensitive. Redaction occurs before persistence and before API, report, UI,
   log, or artifact projection, not only at final display time.
2. Redaction uses one project-owned structured boundary with tests for encoded,
   nested, and partial secret forms. Failure messages exposed outside the
   process use stable categories and safe summaries rather than raw exception
   text.
3. Every dynamic Markdown or HTML report field is escaped or rendered through
   a safe structured renderer. This includes event data, Provider output,
   deterministic text, action and verification text, memory, and all Agent
   fields; the V7 Agent-text sanitizer is not the only protected path.
4. Reports show each cited Evidence ID together with its Provider-result
   status. Failed and skipped sources remain visible as collection outcomes but
   are never presented as supporting evidence.

#### 2.9.3 Human Action And Verification State

The backend owns state-transition validation; the frontend may constrain its
controls but is not a security or integrity boundary.

For an action with `requires_approval=false`, allowed transitions are:

```text
proposed -> done | rejected | skipped
```

For an action with `requires_approval=true`, allowed transitions are:

```text
proposed -> approved | rejected | skipped
approved -> done | skipped
```

`done`, `rejected`, and `skipped` are terminal. A high-risk action requires a
non-blank human approval note before entering `approved`; that approval note
must remain attached when the action later enters `done`. No API may interpret
`approved` or `done` as proof that DiagOps executed a production mutation.

A verification may move only from `pending` to `passed`, `failed`, or
`skipped`; terminal verification states cannot be rewritten. `passed` and
`failed` require all of the following:

1. A non-blank human result note.
2. At least one valid result Evidence ID from a successful or partial Provider
   result.
3. At least one valid related action ID or cause type.

All supplied evidence, action, and cause references must resolve inside the
same investigation. `VerificationSuggestion` and its PATCH request add these
JSON-compatible fields:

```text
result_evidence_ids: string[] = []
related_action_ids: string[] = []
related_cause_types: CauseType[] = []
```

At least one of `related_action_ids` or `related_cause_types` is non-empty for
`passed` and `failed`. Old records without these additive fields deserialize to
empty lists and remain readable, but a new state transition must satisfy the
V8.1 contract.

Unknown investigation or child IDs return `404`. A well-formed request that
violates a transition, approval, reference, or stale-write rule returns `409`
with a stable safe error code. Request-shape and enum validation remains
`422`.

#### 2.9.4 SQLite Schema, Atomicity, And Lifecycle

1. SQLite uses an explicit, ordered schema-version manifest. Startup applies
   every missing migration exactly once in a transaction, then validates the
   recorded version and required tables, columns, indexes, and foreign keys.
   `create_all` or table-existence checks are not a migration substitute.
2. Every SQLite connection enables and verifies `PRAGMA foreign_keys=ON`.
   Tests open a database created at each supported historical version and
   prove migration, referential integrity, and restart readability.
3. Updating an investigation must not delete and reinsert its parent row.
   Aggregate writes use one transaction and preserve child-row identity and
   foreign-key validity.
4. Action and verification PATCH operations update only the targeted child
   record atomically. They use a persisted revision or an equivalent
   compare-and-swap condition so concurrent stale updates fail with a conflict
   instead of losing another writer's change.
5. `sqlite:///:memory:` uses a shared connection pool appropriate for one
   process and disables the same-thread driver check only at the engine
   boundary. Container construction and shutdown own engine lifetime; request
   handling must not recreate, dispose, or silently replace the repository.
6. V7 findings, executions, review, run attribution, and final investigation
   projection are committed as one logical result. Either the complete valid
   result is readable, or the deterministic investigation remains readable
   with a structured Agent-persistence failure; a half-written review must
   never appear complete.

#### 2.9.5 Orchestration, API, And Frontend Resilience

1. Optional LLM and Agents SDK construction, execution, validation, and
   persistence failures preserve the deterministic hypotheses, report,
   actions, and verification suggestions. Optional enrichment never turns a
   completed deterministic investigation into an API failure.
2. The live gate validates claims about executed actions across every clean,
   partial, malformed, injection, and fallback row. It does not infer safety
   from only the canonical clean rows.
3. Add `GET /investigations/summaries` for the workbench so listing
   investigations does not deserialize or transfer reports, evidence, Agent
   traces, and other detail collections. Preserve the existing
   `GET /investigations` full-record list as a read-only compatibility API
   during V8.1; the frontend moves to the summary contract. The new endpoint
   returns newest-first `InvestigationSummary` records containing only `id`,
   `status`, `service`, `title`, `top_cause_type`, `confidence`,
   `action_count`, `verification_count`, and safe `failure_reason`.
4. Workbench detail resources load independently. One failed optional endpoint
   shows a local unavailable state while already successful event, evidence,
   report, action, verification, or Agent sections remain usable.

#### 2.9.6 V6 And Pseudo-LLM Compatibility Boundary

V8.1 removes runtime behavior that has been superseded, while retaining
readability of historical records:

1. Remove `ReActInvestigationAgent`, ReAct settings and container wiring, its
   execution and write path, the frontend ReAct panel, and tests whose only
   purpose is to require that retired runtime or UI behavior.
2. Remove `ReadOnlyLlmAnalyst`, its settings and container wiring, and its
   execution and write path. Future optional analysis uses only the unified
   Agents SDK runtime and must satisfy the current evidence contract.
3. Keep the `react_traces` and `llm_analyses` tables, their domain reader
   models, deserialization support, and read-only compatibility APIs. Existing
   rows remain readable after restart; V8.1 creates no new rows in either
   table.
4. Keep focused SQLite and API tests that prove historical ReAct traces and LLM
   analyses remain readable. Delete broad runtime, writer, configuration, and
   frontend tests only when their production behavior is removed in the same
   change.
5. Historical specs and plans remain immutable records. V4 and V5 public or
   persisted contracts remain supported unless this spec names a replacement
   and its compatibility behavior explicitly.
6. Any future ReAct-like follow-up evidence behavior must use the unified
   Agents SDK runtime under a separately approved design; it must not revive
   the V6 implementation.

## 3. Product Decisions

1. Reliability is the primary goal.
2. Deterministic RCA remains the fallback and safety baseline.
3. Existing Specialist roles, evidence validation, persistence, and workbench
   contracts are reused.
4. Provider compatibility is explicit: V8.1 supports `openai` and `deepseek`.
5. Both providers use the same project-owned orchestration and domain models.
6. There is no provider router, automatic fallback, or mixed-provider run.
7. Provider-specific transport differences stay behind one small adapter.
8. Live certification is recorded per provider and does not block the core
   V8.1 release when credentials for an optional provider are unavailable.
9. Baseline hardening is part of V8.1 and precedes paid reliability claims.
10. V6 ReAct and pseudo-LLM write paths are retired; historical reads are
    preserved.

## 4. Non-Goals

V8.1 does not implement:

1. Follow-up evidence requests or a third Specialist round.
2. New Agent roles, generic Agent frameworks, or model routing.
3. Automatic Provider fallback or mixed-provider execution.
4. User-configurable Base URLs or arbitrary compatible endpoints.
5. RAG, embeddings, vector search, or knowledge graphs.
6. Shell, SQL, browser, filesystem, SSH, or generic HTTP tools.
7. Automatic remediation, rollback, restart, scaling, or configuration changes.
8. Queues, distributed workers, LangGraph, or pause/resume.
9. A new frontend route or graph library.
10. Dropping or rewriting historical `react_traces` or `llm_analyses` data.
11. Removing V4 or V5 public and persisted contracts that are not explicitly
    replaced by this design.

## 5. Hybrid Agreement Contract

V8.1 aligns code, tests, reports, UI, and acceptance scoring around one rule:

```text
non-low-confidence deterministic baseline
  + at least one matching active Specialist root_cause
  + no alternative active root_cause
  + no contradiction
  + completed mandatory Agent steps
  = agreement
```

Rules:

1. A `signal` or `gap` finding cannot independently produce `agreement`.
2. An alternative active `root_cause` or contradiction produces `conflict`.
3. A low-confidence or `unknown` baseline requires two distinct matching
   Specialist `root_cause` findings before `agent_leads` may select a cause.
4. Invalid evidence references are rejected before arbitration.
5. User-visible wording is `确定性 RCA 与 Agent 复核一致`; it must not claim
   multiple Specialists agreed when only one Specialist corroborated the
   deterministic baseline.

## 6. Safe Execution Diagnostics

Reliability artifacts add a safe execution-step projection:

```text
step_kind
agent_name
analysis_round?
attempt
status
failure_category
evidence_ids[]
```

The projection covers Coordinator and Specialist executions. It excludes task
descriptions, prompts, raw responses, reasoning, free-text errors, provider
payloads, URLs, and credentials.

`step_kind` is one of:

```text
initial_coordination
specialist_collection
specialist_recollection
final_synthesis
reference_validation
hybrid_arbitration
review_persistence
```

`failure_category` is one of:

```text
none
not_configured
authentication
rate_limit
quota
timeout
cancelled
transport
invalid_output
invalid_reference
missing_specialist
unsafe_output
persistence
unknown
```

The category is produced at the boundary that observes the failure. It is not
reconstructed from free-text `error_message`. Existing error text may remain
for internal logs after redaction, but API, UI, and artifacts use the stable
category.

The evaluator derives from structured data:

1. Missing mandatory Agents or rounds.
2. Failed, skipped, invalid-output, timeout, and fallback categories.
3. Agreement-contract validity.
4. Valid and invalid evidence references.

### 6.1 Persistent Run Attribution

Provider, model, and safe failure state must remain readable after restart.
Add backward-compatible fields to the persisted coordination review:

```text
model_provider: openai | deepseek | null = null
model_name: string | null = null
primary_stabilization_category: StabilizationCategory | null = null
secondary_stabilization_categories: StabilizationCategory[] = []
```

Rules:

1. `model_provider` and `model_name` identify the single selected model path;
   they never contain keys, endpoints, deployment URLs, or account identifiers.
2. V1-V7 reviews deserialize with null attribution and empty categories.
3. A real V8.1 review requires provider and model; deterministic/custom reviews
   may keep both null.
4. Failed or skipped runs without a review retain provider, model, and the
   derived stabilization categories in `MultiAgentRunSummary`, using persisted
   execution records as the source.
5. `AgentExecution` adds `step_kind`, `attempt`, `failure_category`,
   `model_provider`, and `model_name` with backward-compatible defaults. These
   fields are persisted by both memory and SQLite repositories, allowing failed
   runs without a review to retain attribution.
6. The workbench reads attribution and failure categories from persisted
   structured fields, never from current process environment or free-text error
   parsing.
7. API changes are additive. Frontend types treat new fields as optional when
   reading V1-V7 records.

Persistence and API tests must cover memory and SQLite round-trip, process
restart readability, old payload defaults, workbench response shape, and
unknown-investigation 404 behavior.

## 7. Provider Configuration

Add one explicit setting:

```text
agents.provider: openai | deepseek = openai
```

Environment override:

```text
DIAGOPS_AGENTS_PROVIDER=openai|deepseek
```

OpenAI keeps the existing configuration and behavior.

DeepSeek configuration uses local process environment values:

```text
DIAGOPS_AGENTS_PROVIDER=deepseek
DIAGOPS_AGENTS_MODEL=<supported DeepSeek model>
DEEPSEEK_API_KEY=<local process environment only>
```

Rules:

1. OpenAI remains the default, so existing YAML requires no migration.
2. DeepSeek uses its official OpenAI-compatible API endpoint.
3. The endpoint is fixed in the adapter and is not user-configurable in V8.1.
4. The model name is explicit and must not be silently substituted.
5. Missing or blank key/model produces a visible `skipped` Agent run and no
   network call.
6. A DeepSeek failure never falls back to OpenAI, and an OpenAI failure never
   falls back to DeepSeek.
7. Every live run records exactly one provider and model.
8. Provider implementation state and live certification state are separate:
   key-free contract tests may prove `implemented`, while only the paid live
   gate may prove `certified`.

## 8. OpenAI-Compatible Adapter Boundary

V8.1 keeps one Agent runtime. The adapter translates only transport and
structured-output differences required by the selected provider.

The DeepSeek path must:

1. Use the provider's documented OpenAI-compatible chat/tool interface.
2. Declare the required capability profile at startup: chat completions,
   function/tool calls, JSON object output, and local schema validation.
3. Use strict function schemas when the certified endpoint documents them. If
   a required capability is unavailable, mark the Provider `unsupported` and
   make no Agent call; never silently downgrade to a looser contract.
4. Validate every structured Specialist and Coordinator result locally with
   the existing Pydantic contracts.
5. Reject empty output, Markdown fences, prose wrappers, invalid JSON, and
   schema mismatches.
6. Never repair or heuristically extract invalid JSON.
7. Map authentication, quota, rate-limit, timeout, and invalid-output failures
   into existing safe Agent execution categories.
8. Disable sensitive trace export when the selected provider cannot guarantee
   the existing redaction boundary.

Capability checks use the selected, documented Provider profile; V8.1 does not
probe arbitrary endpoints or infer support from a failed paid request. Official
model names, endpoints, tool-call behavior, and structured-output capabilities
are verified immediately before certification and recorded without sensitive
connection data.

The adapter must not become a generic Provider factory or expose arbitrary
OpenAI-compatible Base URLs. Additional compatible providers are added only
after a concrete provider contract and tests exist.

## 9. Evaluation Runner And Artifacts

V8.1 adds one project-owned evaluation command with two modes:

```text
deterministic
live
```

`deterministic` uses model substitutes and fault injectors. `live` requires an
explicit provider configuration and uses only simulated incident data.

Each run writes schema-v3 JSON and a short Markdown summary under
`output/reliability/<run-id>/`.

Schema rules:

1. Existing schema-v1 and schema-v2 files under `artifacts/` remain immutable
   historical inputs; no migration or rewrite occurs.
2. V8.1 writes only schema v3 under `output/reliability/`.
3. A schema-v3 live artifact requires non-empty `provider` and `model`.
4. A deterministic artifact uses `provider=substitute` and its deterministic
   substitute name as `model`; the fields are never omitted.
5. Readers reject unsupported future schema versions instead of guessing.
6. Schema-v3 additions are additive; removing or renaming fields requires a
   later schema version.

Minimum artifact fields:

```text
schema_version
run_id
mode
provider
model
started_at
completed_at
case_results[]
aggregate
```

Each case records the expected and selected cause, decision status, reference
validity, safe fallback category, duration, token usage and estimated cost when
available, execution-step projection, execution failure categories, review-level
stabilization categories, and pass/failure state.

Aggregates include:

1. Expected-cause match rate.
2. Evidence-reference validity rate.
3. Decision consistency by case.
4. Partial and fallback rates.
5. Agreement-contract validity.
6. Missing or failed mandatory steps by Agent and round.
7. Latency percentiles, tokens, and estimated cost when available.
8. Provider and model attribution.

Artifacts must not contain API keys, Base URLs, full prompts, raw responses,
reasoning, free-text model output, or raw provider payloads.

## 10. Fault Injection

Deterministic tests cover:

1. Specialist timeout.
2. Malformed structured output.
3. Unknown evidence ID.
4. Coordinator invalid output or failure.
5. Prompt-injection text inside untrusted evidence.
6. Missing Specialist recollection without repeating valid Specialists.
7. Unknown or duplicate Specialist output.
8. Signal-only corroboration attempting to produce `agreement`.
9. Valid hybrid agreement with one matching Specialist `root_cause`.
10. Provider authentication, quota, rate-limit, timeout, and empty-output
    failures.

Every failure preserves deterministic RCA and remains visible through a safe
structured category.

## 11. User-Visible Behavior

The existing workbench shows:

1. Deterministic baseline and Agent decision.
2. Accepted Specialist findings and evidence IDs.
3. Mandatory execution-step status.
4. Partial, invalid-output, timeout, skipped, and fallback categories.
5. Provider and model used for the run.
6. Provider implementation and certification status without implying an
   untested Provider is reliable.

The UI distinguishes facts, Agent inference, deterministic inference,
recommendations, and uncertainty. It never displays raw chain-of-thought or
claims that a production action was executed.

## 12. Safety And Error Handling

1. Production systems remain read-only.
2. Unknown or invalid model output is rejected before persistence or
   arbitration.
3. Provider failures preserve the deterministic investigation result.
4. Logs and artifacts never contain credentials or sensitive model content.
5. Evidence, logs, alerts, service metadata, and memory are treated as
   untrusted data and cannot change tools, policy, or system instructions.
6. Evaluation artifact write failure fails the evaluation command, not the
   investigation.
7. Mock evidence cannot enter manual or webhook investigations.
8. Failed or skipped Provider output cannot support a root cause.
9. All persisted and user-visible dynamic data passes the V8.1 redaction and
   safe-rendering boundary.
10. Invalid action, verification, reference, migration, or concurrent-write
    transitions fail closed with a stable client-safe error.

## 14. Live Certification

The canonical five-case, three-run-per-case gate runs independently for each
configured provider.

Core V8.1 acceptance requires at least one configured provider to pass:

1. 15/15 investigations return a valid review or explicit fallback without a
   process crash.
2. Evidence-reference validity is 100%.
3. Expected final cause matches at least 12/15 runs.
4. Every case has the expected safe outcome in at least 2/3 runs.
5. Agreement-contract validity is 100%.
6. Unsupported production action execution count is zero.
7. Every `partial` row exposes a safe mandatory-step category.
8. Executed-action claim validation passes across all clean and adversarial
   artifact rows.

Implementation state is recorded per provider:

```text
implemented
unsupported
```

`implemented` requires all key-free capability, validation, redaction, and
failure-mapping tests. `unsupported` means a required capability profile is
not available and no Agent request is made.

Certification is recorded independently per implemented provider:

```text
certified
failed
not_run
```

An optional provider with missing credentials is `not_run`; it does not block
the core release. Documentation must not call that provider certified until
its own gate passes. Provider model names, endpoints, structured-output
capabilities, and prices must be checked against current official documentation
immediately before a paid run.
