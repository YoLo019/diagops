# DiagOps V8.2 Bounded Follow-Up Evidence Design

## 1. Goal

V8.2 adds one bounded, read-only evidence follow-up round to the reliable V8.1
multi-agent RCA runtime.

The model may propose what evidence is missing, but deterministic DiagOps code
decides whether a request is safe, justified, and inside budget. Follow-up may
revise a decision without erasing the initial decision or deterministic RCA.

## 2. Entry Gate

V8.2 starts only when all conditions are true:

1. V8.1 acceptance criteria pass.
2. At least one model Provider has `certified` live status.
3. A V8.1 schema-v3 artifact contains concrete cases where missing retrievable evidence,
   rather than prompt, schema, arbitration, or provider transport failure,
   caused a wrong, partial, or fallback result.
4. The expected follow-up evidence exists through current read-only Provider
   tools.
5. Every proposed V8.2 acceptance case appears in a reviewed, versioned entry
   manifest generated from accepted V8.1 structured results.

If the artifact does not prove this need, V8.2 is skipped. A third Agent round
is not added speculatively.

The entry manifest contains no prompt, response, reasoning, free-text model
output, credential, URL, or raw Provider payload. Each case records:

```text
schema_version
v8_1_run_id
case_id
initial_decision_status
initial_selected_cause_type?
primary_stabilization_category
retrievable_gap: true
evidence_provider
evidence_source_id
expected_tool
expected_strategy
expected_signal_kind
expected_safe_outcome
```

Only cases with `retrievable_gap=true` may justify V8.2. `expected_tool`,
`expected_strategy`, and `expected_safe_outcome` are fixed before V8.2 runs so
necessary-request recall and unnecessary-request rejection remain measurable.

## 3. Product Decisions

1. One follow-up round per investigation.
2. At most three approved read-only tool calls.
3. The selected V8.1 model Provider remains selected for the whole run.
4. Models propose; deterministic code validates and executes.
5. Tool inputs come from persisted incident data and approved strategy, never
   from model-provided paths, URLs, queries, credentials, or configuration.
6. Only affected Specialists review new evidence once.
7. Final arbitration remains deterministic.
8. Initial and final state remain independently readable.

### 3.1 Provider Terminology

V8.2 keeps these identities separate:

```text
model_provider       # openai | deepseek, inherited from V8.1
evidence_provider    # log | metric | deploy | dependency
evidence_source_id   # stable concrete source, for example prometheus-primary
```

The selected `model_provider` and model remain unchanged for the entire Agent
run. Deterministic code derives `evidence_provider` and `evidence_source_id`
from persisted Provider results; the model cannot choose or alter them.

## 4. Non-Goals

V8.2 does not implement:

1. New model providers or Agent roles.
2. More than one follow-up round or three approved calls.
3. Free-form queries, generic HTTP, shell, filesystem, SQL, SSH, or MCP tools.
4. A generic policy engine or orchestration framework.
5. Automatic remediation or production mutation.
6. New queues, workers, checkpoints, or pause/resume.
7. Context refresh for memory or service catalog in the first release.
8. Raw chain-of-thought display.

## 5. Supported Follow-Up Strategies

V8.2 starts with only two strategies:

```text
retry_failed
expand_window
```

Rules:

1. `retry_failed` is valid only when the latest corresponding Provider result
   for the same `evidence_source_id` is `failed` or `partial`.
2. `retry_failed` invokes only that concrete evidence source. It must not
   recollect every Provider sharing the same `EvidenceProvider` enum.
3. `expand_window` is initially valid only for log and deployment evidence,
   whose current Provider contracts use `IncidentEvent.time_window_minutes`.
   Metrics and dependencies are excluded until their Provider explicitly
   supports range queries.
4. Expanded windows are twice the incident time window and capped at 180
   minutes.
5. A source/tool/strategy tuple may run at most once.
6. Equivalent successful evidence already collected during the investigation
   is not fetched again.
7. `refresh_context` is excluded until a real freshness contract exists for
   memory and service catalog Providers.

V8.2 adds a stable `evidence_source_id` to persisted `ProviderResult` records.
Configured evidence sources receive stable project/operator-defined IDs.
Existing V1-V8.1 results deserialize as `legacy:<evidence_provider>`; because
that value may represent multiple concrete sources, legacy results are visible
but are not eligible for `retry_failed`. No model output participates in source
identity or migration.

Supported tools are the existing registered read-only Provider tools:

```text
read_logs
query_metrics
read_deployments
query_dependencies
```

The runtime reads the registered `ToolSpec` and rejects tools not marked
`read_only=true`. `retry_failed` may use all four tools. `expand_window` may use
only `read_logs` and `read_deployments` in V8.2. The policy passes a derived
copy of the persisted incident with the bounded time window; model-provided
tool inputs are ignored and rejected as `scope_not_allowed`.

The tool execution boundary must support selecting one concrete
`evidence_source_id`. The existing behavior that invokes all sources with the
same evidence enum is not valid for V8.2 retry execution.

## 6. When Follow-Up Is Allowed

Follow-up may be proposed only after the initial V8.1 hybrid decision and when
at least one condition holds:

1. Decision is `conflict`, `agent_leads`, or `fallback`.
2. A valid Specialist finding records an explicit retrievable evidence gap.
3. A relevant Provider result is `failed` or `partial`.

An `agreement` decision without a retrievable evidence gap performs no
follow-up.

## 7. Domain Contracts

Add structured, JSON-compatible contracts.

### 7.1 FollowUpEvidenceRequest

```text
id
tool_name
strategy
reason
expected_signal
evidence_provider
evidence_source_id
status
tool_call_id?
output_evidence_ids[]
policy_reason?
failure_category?
duration_ms
created_at
completed_at?
```

The model may populate only `tool_name`, `strategy`, `reason`, and
`expected_signal`. DiagOps owns every other field. `failure_category` reuses
the V8.1 `FailureCategory`; V8.2 adds no second error enum.

### 7.2 Statuses

```text
proposed -> rejected | approved
approved -> completed | failed | interrupted
```

Rejected requests use a stable reason:

```text
round_exhausted
budget_exceeded
unknown_tool
not_read_only
strategy_not_allowed
not_justified
duplicate_request
scope_not_allowed
```

### 7.3 Specialist Revision

Extend the V8.1 round and phase contracts additively:

```text
analysis_round: 1 | 2 | 3
analysis_phase: initial | conflict_review | follow_up_review
```

The mapping is fixed:

```text
1 -> initial
2 -> conflict_review
3 -> follow_up_review
```

`AgentFinding`, `DiagnosisTask`, `AgentExecution`, persistence payloads, API
models, and frontend types use the same round mapping. V1-V8.1 records keep
their existing round and receive the matching phase default.

A `follow_up_review` finding:

1. Revises the latest valid finding from the same Specialist.
2. Cites at least one approved follow-up evidence ID, unless it explicitly
   withdraws because follow-up failed.
3. Never overwrites prior findings.
4. Is rejected before persistence when references are invalid.

### 7.4 Coordination Review

Extend the V8.1 persisted review with additive fields:

```text
initial_decision_status?
initial_selected_cause_type?
final_decision_status?
final_selected_cause_type?
follow_up_requests[]
follow_up_started_at?
follow_up_completed_at?
```

Rules:

1. V8.1 `decision_status` and `selected_cause_type` populate the initial fields
   before any proposal is validated.
2. Existing public `decision_status` and `selected_cause_type` represent the
   final result after V8.2, preserving current consumer behavior.
3. Initial fields are immutable after first persistence.
4. V1-V8.1 records deserialize with null initial/final fields and an empty
   request list; read-time adapters may expose existing decision fields as the
   effective initial and final value without rewriting stored history.
5. The review retains V8.1 `model_provider`, `model_name`, execution failure
   categories, and stabilization categories.

### 7.5 V8.1 Execution Contract Extension

V8.2 reuses V8.1 `FailureCategory`, `StabilizationCategory`, provider/model
attribution, and execution projection. It adds these `step_kind` values:

```text
follow_up_policy
follow_up_tool
follow_up_specialist_review
follow_up_arbitration
```

Every V8.2 execution retains `attempt`, `analysis_round`, `failure_category`,
`model_provider`, and `model_name`. Review-level failures use the existing
primary and secondary `StabilizationCategory` fields.

## 8. Deterministic Policy

Validation order:

1. Follow-up round remains available.
2. Approved-call count remains below three.
3. Tool exists in the current registry.
4. Tool is read-only.
5. Strategy is allowed for the tool.
6. The derived evidence source exists, is unambiguous, and matches the tool.
7. Current conflict, retrievable gap, failed, or partial state justifies the
   request.
8. The same source/tool/strategy has not already succeeded.
9. Derived input stays inside time-window and configuration limits.

Rejected requests are persisted but create no tool call. Model-provided extra
scope is rejected and never partially honored.

## 9. Runtime And Stop Rules

1. Coordinator proposes zero to three structured requests.
2. Policy validates every request.
3. Approved calls execute once using derived inputs.
4. Calls reaching the deadline fail visibly; arbitration continues with
   completed evidence.
5. Only Specialists affected by completed or failed follow-up calls review the
   result once.
6. No tool call starts after final arbitration begins.
7. Rejected or failed follow-up cannot increase confidence.
8. A partial follow-up cannot create new `agreement`.
9. If every affected review fails, retain the initial valid decision or use
   deterministic fallback.

## 10. Persistence And Recovery

V8.2 reuses existing review, finding, execution, evidence, and tool-call
persistence. No new table is required initially.

Follow-up requests live in the versioned coordination-review payload. Recovery
contract:

1. DiagOps allocates both request ID and tool-call ID before execution.
2. Approval atomically saves the complete review containing the approved
   request and preallocated `tool_call_id` before the Provider is invoked.
3. `ToolCallRecord` adds optional `follow_up_request_id`; the executed record
   must contain both preallocated IDs.
4. Saving the terminal tool call, new evidence, and terminal request status uses
   one SQLite transaction. The in-memory repository applies the same operation
   as one method call.
5. A successful existing tool call is never executed again after restart.
6. Restart recovery is display-only; it never automatically resumes an
   incomplete follow-up.
7. An approved request without a terminal tool call becomes `interrupted`.
8. A terminal tool call whose request update was interrupted is deterministically
   linked through `follow_up_request_id` and the preallocated `tool_call_id`;
   read-time reconstruction reports it as interrupted and never repeats it.
9. Initial decision fields are never replaced by final decision fields.
10. The final review is published only after all references validate.

Repository APIs must expose one transaction-scoped operation for terminal
follow-up persistence. A sequence of independent `save_review`, `save_tool_call`,
and `save_evidence` calls does not satisfy this atomicity requirement.

If implementation cannot satisfy atomicity and idempotency with the existing
payload, a separate table requires a new reviewed spec amendment; it is not
pre-authorized here.

## 11. API And Replay

Existing endpoints expose additive fields only:

```text
GET /investigations/{id}/agent-findings
GET /investigations/{id}/coordination-review
GET /investigations/{id}/tool-calls
GET /investigations/{id}/agent-executions
GET /investigations/{id}/rca-workbench
```

The workbench timeline shows:

1. Initial deterministic and Agent decision.
2. Proposed requests and expected signals.
3. Policy approval or stable rejection reason.
4. Tool-call status and output evidence IDs.
5. Specialist revisions.
6. Final decision and whether it changed, strengthened, weakened, or stayed
   unchanged.
7. Failed, partial, interrupted, and fallback states.
8. The inherited V8.1 model Provider/model and structured execution failure
   categories.

## 12. Evaluation

V8.2 extends the V8.1 schema-v3 runner additively. It does not create another
artifact format, error enum, or output directory. Provider/model remain required
and existing V8.1 fields retain their meaning.

Each V8.2 case adds:

```text
entry_manifest_case_id
initial_decision_status
initial_selected_cause_type?
final_decision_status
final_selected_cause_type?
follow_up_requested
approved_request_count
rejected_request_count
completed_request_count
interrupted_request_count
wrong_to_correct
correct_to_wrong
additional_duration_ms
additional_input_tokens?
additional_output_tokens?
additional_estimated_cost?
```

Aggregates extend the V8.1 runner with:

1. Initial and final expected-cause match rates.
2. Necessary-request recall.
3. Unnecessary-request rejection rate.
4. Follow-up policy acceptance and rejection counts.
5. Correct-to-wrong and wrong-to-correct decision transitions.
6. Additional latency, tokens, and cost per corrected case.
7. Partial, interrupted, and fallback rates.
8. Evidence-reference validity after follow-up.

The gate must not reward a model merely for requesting more tools.
Necessary and unnecessary requests are scored only against the reviewed entry
manifest fixed before execution. Requests not represented by a manifest case
are evaluated by deterministic policy but cannot retroactively change the
ground truth.

## 13. Fault Injection

Required deterministic scenarios:

1. Unsupported or non-read-only tool request.
2. More than three proposed calls.
3. Duplicate successful source/tool/strategy request.
4. Provider returns `partial` during follow-up.
5. Follow-up evidence contains prompt-injection instructions.
6. Specialist cites an unknown follow-up evidence ID.
7. Final Coordinator call fails after valid revisions exist.
8. Process interruption before tool execution.
9. Process interruption after tool completion but before review persistence.
10. Restart does not repeat a successful tool call.
11. Two concrete evidence sources sharing one `EvidenceProvider` enum retry
    only the failed `evidence_source_id`.
12. `expand_window` changes the derived incident window for logs/deployments and
    is rejected for metrics/dependencies.

Every case preserves the initial review and deterministic RCA.

## 14. Configuration

Add one setting:

```text
agents.follow_up_enabled: false
```

Environment override:

```text
DIAGOPS_AGENTS_FOLLOW_UP_ENABLED
```

V8.1 Agents and V8.2 follow-up must both be enabled. The selected V8.1
`model_provider` and model are inherited without another selector. The
one-round and three-call limits are fixed product policy, not configuration
knobs.

## 15. Tests And Acceptance Criteria

Automated tests must prove:

1. Follow-up entry conditions and tool/strategy rules.
2. At most three approved calls and no second round.
3. Rejected requests create no tool calls.
4. Approved requests use derived, bounded inputs.
5. Follow-up evidence persists before Specialist revision.
6. Only affected Specialists review once.
7. Final arbitration uses latest valid findings.
8. Initial state remains readable after success or failure.
9. Persistence transitions are atomic and restart-safe.
10. Successful calls are not repeated after restart.
11. V1-V8.1 records deserialize with safe defaults.
12. Round 3 and `follow_up_review` round-trip through memory, SQLite, API, and
    frontend types while earlier rounds remain compatible.
13. Provider/model, V8.1 execution categories, and initial decision fields
    survive successful, failed, and interrupted follow-up.
14. Preallocated IDs and `follow_up_request_id` reconstruct interrupted tool
    calls without repeating execution.
15. Terminal request, tool call, and evidence persistence is atomic.
16. Schema-v3 artifacts retain every V8.1 required field and add only the V8.2
    fields defined in section 12.
17. Entry-manifest fixtures define necessary and unnecessary requests before
    evaluation.
18. API additions remain backward compatible and unknown investigations return
    404.
19. UI wording never claims a production action was executed.

Standard verification:

```powershell
uv run ruff check .
uv run pytest -v
Set-Location frontend
npm.cmd run build
```

## 16. Live Gate

Run the five simulated cases three times with one V8.1-certified provider.

Thresholds:

All V8.1 live thresholds remain mandatory, including agreement-contract
validity, Provider/model attribution, structured partial categories, prompt
injection safety, mandatory-step completeness, and zero wrong agreement.

Additional V8.2 thresholds:

1. 15/15 runs return a valid final review or explicit fallback without a
   process crash.
2. Evidence-reference validity is 100%.
3. Unsupported or mutation tool execution count is zero.
4. Expected final cause matches at least 12/15 runs.
5. Every case has the expected safe outcome in at least 2/3 runs.
6. Follow-up never changes a correct initial decision into a wrong final
   decision.
7. Every required follow-up case executes at least one justified request in at
   least 2/3 attempts.
8. Every unnecessary or out-of-scope request is rejected.
9. The degradation case preserves deterministic RCA in 3/3 runs.
10. Latency, tokens, cost, correction benefit, partial rate, interrupted rate,
    and fallback rate are reported.
11. Every V8.2 row links to a pre-run entry-manifest case or is explicitly
    marked as a policy-only negative case.
12. Every follow-up execution retains the V8.1 model Provider/model and uses no
    mixed or fallback model Provider.

Other V8.1-supported providers may run independent certification later and do
not block V8.2 core completion.

## 17. Rollout

1. Confirm the V8.1 artifact proves retrievable evidence gaps and approve the
   versioned entry manifest.
2. Add stable evidence-source identity and migration defaults.
3. Add V8.1-compatible round, phase, decision, execution, and policy contracts
   with tests.
4. Add bounded runtime and interruption tests.
5. Add transaction-scoped persistence and recovery behavior.
6. Add report, API, and replay fields.
7. Extend the schema-v3 evaluation runner and fault injection.
8. Run standard verification.
9. Run the live gate with one certified model Provider.

## 18. Acceptance Summary

V8.2 is complete when:

1. V8.1 data justifies follow-up evidence collection.
2. Every acceptance case is fixed in a reviewed entry manifest before runs.
3. Coordinator proposals cannot bypass deterministic policy or choose an
   evidence source.
4. At most one round and three read-only calls execute.
5. Retry targets one concrete failed evidence source, and expanded windows are
   used only by Providers that honor them.
6. Follow-up can revise a decision without erasing history.
7. Interrupted runs do not duplicate successful calls.
8. Failures preserve a valid initial review or deterministic fallback.
9. V8.1 Provider/model, failure categories, schema-v3 fields, and safety gates
   remain intact.
10. Evaluation proves follow-up does not reduce correctness.
11. Ruff, tests, frontend build, safety scan, artifact scan, and live gate pass.
