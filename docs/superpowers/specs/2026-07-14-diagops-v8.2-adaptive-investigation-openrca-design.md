# DiagOps V8.2 自主调查与 OpenRCA Benchmark 设计

> 状态：已确认。本设计取代 `2026-07-12-diagops-v8.2-bounded-follow-up-evidence-design.md`；旧设计保留为历史记录，不再作为实施依据。

## 1. 背景

V8.1 已完成事件驱动诊断、只读证据采集、确定性 RCA、OpenAI Agents SDK 多 Agent 协作、结构化输出校验、失败降级、持久化和调查台。当前主要不足不是工具只读，而是证据工具仍由固定 Planner 分配，Provider 基本忽略 Agent 提交的查询参数，Specialist 只能分析预先收集的证据。此外，现有验收主要依赖自建样例，缺少公开数据集上的可复现结果。

V8.2 聚焦两个目标：

1. 让 LogAgent、MetricAgent 和 DeploymentAgent 在受限预算内自主、迭代地调用参数化只读工具。
2. 使用 Microsoft OpenRCA 的公开子集，对比固定调查和自主调查的效果，并发布可复现 artifact。

MCP、Skill、通用 Runtime、Trace Agent 和生产写操作不属于 V8.2，延期到后续版本。

## 2. 目标与成功标准

### 2.1 产品目标

- 保留 V8.1 `fixed` 调查策略及确定性降级链路。
- 新增 `adaptive` 调查策略，让 Specialist 直接持有领域工具。
- 工具查询参数实际影响 Provider 返回结果。
- 所有调用具备输入校验、权限约束、预算、去重、超时、脱敏和审计。
- 在现有调查台展示结构化调查轨迹，不展示隐藏 chain-of-thought。
- 使用 40 个固定 OpenRCA 案例对比 `fixed` 与 `adaptive`。

### 2.2 发布门槛

- V8.1 全量回归测试通过，`fixed` 行为无回归。
- 40 个 OpenRCA 案例全部生成官方 Evaluator 可读取的预测。
- `adaptive` Investigation 完成率不低于 95%。
- Evidence 引用合法率为 100%。
- 越权调用和写操作次数为 0。
- `adaptive` 的 OpenRCA 官方部分得分不低于 `fixed`。
- 冻结运行的 manifest、prediction、官方报告和 DiagOps summary 已提交。

准确率不预设虚构数值。若真实结果未满足门槛，保留完整失败结果并继续迭代，不删除不利案例，也不将 V8.2 标记为完成。

## 3. 非目标

- 不增加 SSH、重启、扩缩容、回滚或配置修改能力。
- 不允许任意 PromQL、日志 DSL、文件路径或 Shell 命令。
- 不建设可插拔的通用 Agent Runtime。
- 不新增 MCP Server、Skill 包或插件市场集成。
- 不下载、提交或重新分发完整 OpenRCA 遥测数据。
- 不新增独立 Trace Agent；OpenRCA trace 仅通过依赖关系工具提供受限聚合结果。
- 不要求 DeepSeek 达到与 OpenAI 相同的公开 Benchmark 成绩。

## 4. 总体架构

```text
IncidentEvent
    |
    +-- fixed
    |     `-- 固定 Planner -> 默认查询 -> 确定性 RCA -> 现有多 Agent 复核
    |
    `-- adaptive
          `-- 默认查询形成 Seed Evidence
                -> Coordinator 调用三个 Specialist
                -> Specialist 参数化调用领域工具
                -> 新 Evidence 脱敏、持久化并回传受限投影
                -> Coordinator 处理支持证据、反证和缺口
                -> 必要时触发一次定向复查
                -> 语义引用校验
                -> 失败时保留确定性 RCA
```

V8.2 不复制诊断管线。`adaptive` 复用现有 `DiagnosisOrchestrator`、`AgentsRcaRuntime`、`ToolRegistry`、Provider、Evidence、Task、Execution 和 ToolCall 模型，只扩展策略选择、查询契约和 Specialist 工具配置。

### 4.1 策略选择

- API 请求可显式选择 `fixed` 或 `adaptive`。
- 未指定时读取服务配置，默认值保持 `fixed`，避免升级后意外增加模型费用。
- Demo 与 OpenRCA Benchmark 显式选择 `adaptive`。
- 策略、Adaptive 状态、预算使用量和降级原因进入运行摘要并持久化。

### 4.2 Agent 权限

- LogAgent：`read_logs`。
- MetricAgent：`query_metrics`、`query_prometheus`。
- DeploymentAgent：`read_deployments`、`read_service_catalog`、`query_dependencies`。
- Coordinator 不持有基础设施工具，只负责调用 Specialist、处理冲突并综合结论。
- Adaptive Runtime 只注册 `read_only=True` 的 ToolSpec；发现非只读工具时启动失败并降级到 `fixed`。

## 5. 参数化工具契约

V8.2 复用现有 `ToolSpec.input_schema`，为每个工具绑定 Pydantic 输入模型，不增加另一套 Tool Framework。

### 5.1 公共字段

所有动态查询包含：

- `start_time`、`end_time`：查询窗口。
- `reason`：简短说明本次查询要验证的假设，不是隐藏推理过程。
- `limit`：期望的最大返回数量，只能小于 Host 上限。

`service` 和 `environment` 不由模型提供，始终从 IncidentEvent 注入。

### 5.2 领域字段

- `read_logs`：`keywords`、`levels`、`instance`。
- `query_metrics`：`metric_names`、`aggregation`、`instance`。
- `query_prometheus`：Provider 支持的安全指标模板、聚合方式和窗口参数。
- `read_deployments`：版本、实例和时间范围过滤。
- `read_service_catalog`：当前事故服务的元数据。
- `query_dependencies`：方向、目标依赖和深度；V8.2 深度固定上限为 1。

Prometheus 不接受任意 PromQL。Agent 从 Provider 公布的模板和指标中选择参数，由 Provider 生成查询。日志 Provider 同样不接受任意 DSL 或文件路径。

### 5.3 信任边界

- 查询服务只能是事故服务或 service catalog 已发现的直接依赖。
- 查询窗口必须与事故窗口相交，单次最长两小时。
- Host 强制设置结果数量、单次响应大小和总上下文大小上限。
- 所有模型输入先经 Pydantic 校验，再交给 Provider。
- 参数非法、越权目标和非只读工具均被拒绝并记录失败。
- Provider 返回的文本仍视为不可信输入，沿用 V8.1 脱敏和提示注入边界。

### 5.4 Provider 兼容改造

Provider 协议从：

```python
collect(event)
```

兼容扩展为：

```python
collect(event, query=None)
```

- `query=None` 保持 V8.1 默认采集行为。
- `query` 存在时执行参数化检索。
- Provider 声明支持的 tool name，工具按能力路由，不再仅凭 `EvidenceProvider.METRIC` 等粗粒度枚举选择 Provider。
- 不支持某个查询的 Provider 返回 `SKIPPED`，不得静默忽略参数。

### 5.5 工具结果

Provider 继续输出标准 `ProviderResult` 和 `EvidenceItem`。Tool wrapper 完成脱敏与持久化后，只向模型返回：

- evidence ID；
- 时间和来源；
- 简短 summary；
- 与本次查询直接相关的有限字段；
- partial、empty 或 failed 状态。

完整 payload 不直接放入模型上下文。相同 evidence ID 只保留一次。ToolCallRecord 保存脱敏参数、`reason`、状态、耗时和输出 evidence ID。

## 6. 自主调查循环

### 6.1 第一轮

Coordinator 必须调用三个 Specialist 各一次。每个 Specialist 只接收 IncidentEvent、当前候选根因、对应领域的 Seed Evidence、可用工具和剩余预算。Specialist 可以直接生成 Finding，也可以调用领域工具补足证据。

每次调用按以下顺序执行：

1. SDK 根据 Pydantic 模型生成工具参数。
2. Host 校验权限、时间范围、数量和预算。
3. ToolRegistry 调用目标 Provider。
4. Evidence 脱敏并持久化。
5. 受限 Evidence 投影返回当前 Specialist。
6. Specialist 继续查询或输出结构化 Finding。

### 6.2 第二轮

Coordinator 检查三个 Finding 的支持证据、反证和 gaps。仅当存在冲突或阻塞最终判断的关键缺口时，才调用相关 Specialist 进行第二轮。第二轮复用已收集 Evidence 和剩余预算，不重新调用全部 Agent。

### 6.3 默认预算

- 最多 2 个分析轮次。
- 每个 Specialist 最多 3 次追加工具调用。
- 单个 Investigation 最多 8 次追加工具调用。
- 总 Runtime 沿用现有 60 秒默认超时。
- 不设置最低调用次数，证据充分时允许不调用工具。

预算值保留为已有设置体系中的普通配置，不增加动态预算服务。

### 6.4 停止与去重

出现以下任一条件时停止继续查询：

- 已产生引用合法 Evidence 的 Finding。
- 达到 Specialist 或全局预算。
- 本次查询没有产生新 Evidence。
- 查询与历史查询重复。
- 已进入第二轮。
- Runtime 超时或取消。

重复查询指纹由 `tool_name + 规范化参数` 计算，排除 `reason`，防止模型只修改理由绕过限制。

## 7. 错误处理与降级

- 参数校验失败、越权或重复查询：ToolCall 记为失败或跳过，并占用一次预算。
- Provider partial：保存有效 Evidence，同时向 Agent 返回 warning。
- 查询为空：作为成功的空结果返回，用于排除假设。
- 单个工具失败：Specialist 可使用剩余预算修正一次，或输出 Gap。
- Finding 引用不存在或越域的 Evidence：丢弃该 Finding。
- Specialist 或 Coordinator 失败：Adaptive 状态为 `degraded`。
- Adaptive 超时、取消或无法形成合法 review：保留 V8.1 确定性 RCA、报告和建议。
- OpenAI 不可用时不自动混用 DeepSeek，沿用 V8.1 Provider 隔离规则。

所有尝试，包括在校验阶段拒绝的调用，都写入 ToolCallRecord。调查轨迹通过现有 Task、Execution、ToolCall 和 Evidence 记录组合，不新增独立 Trace 表。

## 8. 根因输出

现有 CauseType 继续作为 DiagOps 内部归一化类别。V8.2 仅增加公开案例实际需要的少量通用类别：

- `resource_saturation`
- `network_fault`
- `configuration_error`
- `process_or_container_failure`
- `infrastructure_fault`

OpenRCA 官方评测允许一个查询包含多个故障，因此 Coordinator 的结构化 Proposal 增加有序的 `root_causes` 列表。每项包含：

- `root_cause_occurred_at`
- `root_cause_component`
- `root_cause_reason`
- `supporting_evidence_ids`

普通 Investigation 可以不返回该列表；OpenRCA Benchmark 至少返回一项，多项按发生时间排列。组件、原因和时间必须由 supporting Evidence 支持；CauseType 不用于替代官方自由文本 reason。现有 `proposed_cause` 继续表示首要的内部归一化类别，保持 V8.1 消费方兼容。

## 9. OpenRCA 子集 Benchmark

OpenRCA 官方仓库为 <https://github.com/microsoft/OpenRCA>。官方说明完整数据包含 Bank、Telecom、Market/cloudbed-1、Market/cloudbed-2 以及日志、指标和 trace，并建议至少准备 80GB 存储和 32GB 内存。V8.2 只提交代码、案例 manifest 和结果 artifact，不提交遥测数据。

### 9.1 固定案例集

选择 40 个案例：

- Bank：10；
- Telecom：10；
- Market/cloudbed-1：10；
- Market/cloudbed-2：10。

选择脚本使用固定随机种子 42，并按 easy、middle、hard、单故障与多故障、根因组件和原因分层。选择发生在首次模型运行之前，manifest 提交后不得按结果替换案例。选择规则不读取任何 DiagOps 预测结果，也不按模型是否答对排除案例。

### 9.2 Ground truth 隔离

`prepare` 命令从用户下载的 OpenRCA 数据生成 runtime-safe case index。该 index 只包含：

- instruction；
- system、date 和 case ID；
- 允许访问的 telemetry 路径；
- 事故时间窗口和服务范围。

`query.csv` 中的 `scoring_points` 和 `record.csv` 只允许 `prepare` 与独立 `evaluate` 命令读取。实际 Benchmark Runtime 只接收 safe index，Provider 只能打开 index 中声明的 telemetry 文件，Agent 不能提交路径。

OpenRCA 时间统一按官方说明使用 UTC+8。safe index 写入带时区时间，Provider 不使用操作系统本地时区做隐式转换。所有 telemetry 路径解析后必须位于配置的数据集根目录内，拒绝绝对路径和目录穿越。

测试必须扫描 safe index、Prompt、Evidence 和 ToolCall artifact，确认不存在 `scoring_points`、record 行或答案字段。

### 9.3 OpenRCA Provider

- `OpenRcaLogProvider`：按时间、关键词、级别和实例查询日志。
- `OpenRcaMetricProvider`：按时间、指标名、聚合方式和实例查询 KPI。
- `OpenRcaDependencyProvider`：从 trace 聚合直接父子组件、延迟和错误关系，通过 `query_dependencies` 返回。

OpenRCA 没有 deployment 数据时，`read_deployments` 返回 `SKIPPED`，不伪造发布证据。

### 9.4 公平对比

`fixed` 和 `adaptive` 使用完全相同的：

- 40 个案例；
- OpenAI 模型和版本；
- Prompt 版本；
- Seed Evidence 生成规则；
- 超时、Token 限制和输出格式。

两种策略都使用同一个 Coordinator 输出契约。差异仅在于 `adaptive` Specialist 可以追加参数化查询。正式发布保存一次冻结运行；额外重复运行只用于观察波动，不作为 V8.2 阻塞项。

### 9.5 指标与 artifact

沿用 OpenRCA 官方字段和 Evaluator：

- root cause occurrence datetime；
- root cause component；
- root cause reason；
- 官方 strict accuracy；
- 官方 partial score。

DiagOps 额外报告：

- Component、Reason、Time 分项准确率；
- Evidence 引用合法率和无效引用数量；
- Investigation 完成率；
- 平均工具调用次数和重复查询拒绝数；
- 平均耗时、输入/输出 Token 和估算成本；
- `fixed` 与 `adaptive` 的分数差异。

冻结目录包含：

- `run-manifest.json`；
- `fixed-predictions.csv`；
- `adaptive-predictions.csv`；
- 官方评测报告；
- `summary.json`。

run manifest 至少记录案例 manifest hash、模型、Prompt 版本、Git commit、策略配置、开始时间和结束时间。

## 10. CLI、API 与 UI

### 10.1 Benchmark CLI

使用标准库 `argparse` 提供一个模块入口和三个子命令：

```text
prepare   生成固定 manifest 与 runtime-safe index
run       按 fixed 或 adaptive 运行并输出 prediction
evaluate  调用官方兼容评分并生成 summary
```

不引入新的 CLI 依赖。

### 10.2 Investigation API

- 创建 Investigation 时接受可选策略。
- Investigation 详情返回策略、Adaptive 状态、预算使用量和降级原因。
- 现有 V8.1 响应字段保持兼容。
- 新字段写入现有 JSON payload，并通过 Pydantic 默认值兼容历史记录；不增加物理列，不提升 SQLite schema version。历史记录读取为 `fixed` 或 `not_applicable`。

### 10.3 Investigation UI

现有详情页增加：

- 策略和 Adaptive 状态；
- 按 Agent、轮次排列的调查轨迹；
- 工具名称、查询意图、脱敏参数、状态和耗时；
- 输出 Evidence 链接；
- 预算使用量和停止原因。

不展示 hidden chain-of-thought。Seed Evidence 与 Adaptive Evidence 通过 ToolCall 输出 ID 关联，不给 Evidence 模型增加重复来源字段。

### 10.4 Benchmark UI

新增只读 OpenRCA 结果页，读取最新冻结 summary，展示：

- Fixed 与 Adaptive 总分和分系统结果；
- Component、Reason、Time 分项；
- 完成率和 Evidence 合法率；
- 调用次数、耗时、Token 和成本；
- 失败案例；
- 模型、Prompt、commit 和运行时间；
- manifest、prediction、report 和 summary 下载入口。

使用现有组件和 CSS，以表格和进度条完成展示，不增加图表依赖。

## 11. 测试与验证

### 11.1 单元测试

- 每个查询模型的有效和无效边界。
- service、environment、时间范围和 limit 强制约束。
- Provider 参数实际影响返回结果。
- Provider tool capability 路由。
- 查询规范化、重复检测和预算。
- Evidence 受限投影与脱敏。
- OpenRCA 输出格式和官方字段投影。
- 单故障和多故障预测的顺序与官方编号格式。

### 11.2 Agent 与集成测试

- Specialist 只能看到领域工具。
- 三个 Specialist 首轮都被调用。
- 只有冲突或关键 gap 触发第二轮。
- partial、empty、failed、timeout 和 cancelled 路径。
- 非法 Evidence 引用被拒绝。
- Adaptive 失败后 Fixed 结果保留。
- 策略、轨迹和降级原因可持久化并通过 API 读取。
- 历史 V8.1 SQLite 数据可迁移和读取。

### 11.3 Benchmark 测试

- 仓库提交人工构造的微型 OpenRCA 格式 fixture，不提交官方遥测。
- `prepare -> run -> evaluate` 在 fixture 上完成 smoke test。
- safe index、Prompt、Evidence 和 ToolCall artifact 的 ground truth 泄漏扫描。
- prediction CSV 与官方 Evaluator 格式兼容。
- manifest hash 和冻结 artifact schema 校验。

### 11.4 前端与发布验证

每次提交执行 Ruff、全量 Python 测试、前端构建和 fixture benchmark smoke test。发布前额外执行 OpenAI live gate、40 案例 Fixed/Adaptive 冻结运行、官方评测、artifact 校验和 README 复现命令。

DeepSeek 仅保留 V8.1 兼容和回归验证，不作为 V8.2 发布阻塞项。

## 12. 实施边界与顺序

实施计划应按以下依赖顺序拆分：

1. 策略与查询领域模型。
2. Provider 参数化和 capability 路由。
3. Specialist SDK tools、预算、去重和降级。
4. 持久化、API 与 Investigation 轨迹 UI。
5. OpenRCA safe adapter、fixture 和 CLI。
6. 40 案例冻结运行与 Benchmark UI。
7. 全量验证、README 和 V8.2 完成审计。

任何阶段都不得以 MCP、Skill、自动修复或通用 Runtime 为由扩大 V8.2 范围。
