## 2. 诊断流程

初始 Evidence → Lead 规划 → 1–3 路独立 Investigator → Critic 审查 → 可选一次补证与复审 → 校验并保存最终决定 → 报告。

### Lead 与 Investigator

Lead 根据事件、初始证据摘要、Provider 可用状态、工具能力和剩余预算分配独立问题。第一轮只调查或有理由地停止，不在尚无候选时要求按候选执行 test。历史 test 动作保持可读。

Investigator 只看到事件、自己的任务、允许的工具、预算及自己的工具结果，不看到兄弟 Agent 的候选和结论。第一轮输出 findings 与候选，事实和推断均有 Evidence 引用。

一次调查轮次可以包含多次“模型选择查询→工具结果入库→模型读取并调整查询”。复用现有 SDK tool continuation，在证据足够、没有有效下一步或剩余预算只够收尾时输出 findings；不能把“最多 2 轮调查”实现成每路只允许一次模型请求。工具次数、模型请求、tokens 和截止时间分别约束这个循环。

Critic 需要补证时，任务必须指定同 run 的 assessment、信息缺口和 expected discriminator，由服务端调度，不再调用 Lead 规划。最多一次补证批次、同时最多 3 路。第二轮只增加 findings、证据和缺口，不新增或改写候选实体／机制，也不强制修订旧 finding。新根因线索未经完整审查不能直接发布；关键替代解释无法排除时 inconclusive。

### Critic

每个候选检查时间、拓扑、机制、影响范围、症状与原因、反证、替代解释七项，输出 accept、reject、needs_evidence 或 inconclusive。pass／fail 引用证据，unknown 说明缺口。

Critic 同时负责跨候选比较：从 accept 的候选中选择最终集合并排序，说明取舍。accept 不等于必定发布。被发布候选不能有 fail 检查；关键 unknown 没有解决时放弃该候选。不适用的检查可以是 unknown，但要解释原因，不能把未知说成已证明。

没有补证时直接给最终决定；有补证时先不发布，补证后只复审一次并给最终决定，不能再请求第三轮。第二轮工具结果必须先入库为 Evidence，再进入 findings 和复审。

默认不追加 Lead 模型调用。旧 lead_adjudication 节点名可保留供历史读取，新诊断中只负责保存 Critic 决定，记录为确定性操作，界面显示“发布诊断”，不冒充 Lead 推理。

## 3. 输出、排序与历史读取

在现有 CoordinationReview JSON 中增加 final_decision：

| 字段 | 含义与校验 |
| --- | --- |
| actor | 默认 critic；Lead 规划提前停止可为 lead，但不能给根因。实验 Lead／Single 分别记录 lead／single，必须与实际执行和配置匹配 |
| action | conclude 或 inconclusive |
| candidate_ids | Agent 排好的候选 ID，无重复；conclude 非空，inconclusive 为空；产品结论只能选择本 run 已 accept 的候选 |
| evidence_ids | 本 run 已提交、状态可用的引用，覆盖候选与最终取舍的证据 |
| summary | 有界公开摘要，说明取舍和不确定性，不保存原始思维链 |
| stop_reason | inconclusive 必填 |

复用现有字段上限、引用和脱敏校验。模型 candidate_ref 由服务端映射到本 run 的候选；模型不能指定所有者或 runtime ID。Lead 规划提前 inconclusive 时保留真实停止决定，后续节点按已有 checkpoint 跳过，不补造 Critic 调用。

报告、API、前端、图、列表、建议、验证记录、重放、diff 和 benchmark 统一使用 final_decision 的顺序。authoritative_candidate_ids 从它派生；原 rank 只保留历史／展示用途，不能再决定新报告的 Top1。未发布候选保留审查结果和排除理由，作为 alternatives 单独展示。

已有 lead_decision 仅保留旧消费者需要的兼容内容，不能成为第二套最终结果。新增字段、发布集合、actor 和 run 归属不一致时显式失败，不能回退到 rank 或 accept 列表猜测结果。所有结论与建议继续要求有效证据引用，确定性代码不创造、替换或重排根因。

**历史兼容只做实现需要的部分。** 继续用现有 v11 Runtime，在运行记录的配置 JSON 中增加 diagnosis_contract_revision=2，用现有摘要校验防止运行中换规则；缺省值按历史 revision 1 读取。旧记录不改 rank、不补造 final_decision；新记录缺必填字段时不能当作旧记录。旧 run 无法由当前版本安全恢复时明确拒绝并允许新建关联诊断，源记录保持不变。无需新表或独立迁移阶段。

## 4. Evidence 与上下文

工具结果在写事务内与最新 Evidence 合并，不能使用入队前的快照覆盖并行工具结果。Investigator 失败后仍将已完成工具的证据合并回阶段投影；发布校验同时检查工具输出的 Evidence 引用。机制说明上限统一为 512 字符，保留有界输出，历史记录继续可读。Critic 的检查保留模型撰写的简短证据适用理由，不能只记录 pass／fail。

支持和反证引用本次 investigation、当前 run 已入库的 success／partial Evidence。failed／skipped 只能解释缺口，不能支持根因。事件、工具和模型输出都按不可信输入校验、脱敏和限长；日志和公开错误不泄露凭据、敏感 payload 或原始异常正文。

| 角色 | 输入范围 |
| --- | --- |
| Lead | 初始摘要最多 6 条，每 kind 最多 2 条；Provider 状态去重，不带错误正文 |
| 第一轮 Investigator | 自己的任务、工具和证据，不带兄弟结论 |
| Critic／复审 | 全部已提交 findings 的有界投影，候选及 assessment 的必需引用，再加最多 4 条未引用证据摘要，每 kind 最多 2 条 |
| 第二轮 Investigator | 目标 assessment、缺口、expected discriminator 和相关证据 |
| 实验 Lead | 保存下来的同一份候选、Evidence 和审查，不增加新遥测 |

findings、候选和已有 assessment 中的支持／反证／检查引用必须保留，不受额外 4 条摘要的配额挤占。摘要先筛同 run 可用证据，再选择内容；同一输入选择确定，不参考 benchmark 标签。

摘要附带可用总数、已包含数、省略数和按 kind 的覆盖信息。没有看到某项信息不等于不存在反证。Critic 有关键缺口时请求定向补证，不能补证时保留缺口并放弃不充分结论。必需输入放不进剩余 token 预算时记录 context_budget_exhausted，不静默删引用或超预算发送。

对省略内容明确区分两条取得路径：

- **已入库但未放入上下文**：摘要保留可定位的 Evidence ID；服务端按任务 evidence_scope 或补证 assessment 投影相关 Evidence 的限长明细。第一轮只读取自己的证据，第二轮可读取明确分配的相关证据；同 run 校验不放宽，读取不新建 Evidence，也不增加第十个工具。若连可定位清单都放不下，明确省略范围，不声称全部可见。
- **查询结果被截断或细节未入库**：返回截断状态、实际返回量和工具支持的过滤能力，由 Investigator 使用原九工具缩小时间窗、实体、实例、关键词或 trace_id 再查，所得结果先形成新 Evidence。只提供对应工具实际支持的字段，不虚构分页能力；来源没有给总量时记未知。

单次结果在 Provider／工具边界过滤、脱敏和限长后入库，不能为以后再读而保存无限原始敏感 payload。累计上下文继续按角色裁剪与保留必需引用，读取明细同样计入模型输入预算。两层限制都要有省略说明；本版不新增 LLM 摘要压缩服务。

partial 的最低覆盖规则继续保留：至少两条不同支持 Evidence；若当前有两种成功 Provider 类型，支持引用覆盖至少两种。**覆盖数量不证明独立性。** Critic 根据已有 provenance 说明是否同源，同一 span 的 trace 和依赖派生、重复查询都不能当作独立佐证。来源不清时保留不确定性，不新增通用来源图。

保留 read_logs、query_metrics、query_traces、read_service_catalog、query_dependencies、read_deployments、read_runtime_state、query_related_alerts、lookup_memory 九工具。工具清单来自现有 registry；调用、重试、恢复都检查只读、参数、实体／时间范围、预算、截止时间和幂等身份。empty、unavailable、partial、failed 和 timeout 保持可区分。

## 5. 预算、重试和恢复

### 预算与重试

2026-09-15 的真实回归显示 Critic 输入约 7–9k Tokens；调查阶段为后续 Critic 及一次纠错预留预算：低额度保留总量的三分之一，高额度以两次收尾输入估算加 Critic 输出上限封顶，同时保留其他活动 Investigator 的收尾额度，避免固定比例预留阻断有余额的纠错。每次输出上限根据当前余额重新计算，不强制比历史最小输出上限递减。strict 工具通道收尾时指定 submit_structured_output，明确告知查询工具已关闭；纠错关闭新查询，但保留该任务已取回的有界证据摘要。纠错累计保留本次逻辑调用的安全错误码；上一版已通过字段校验的草稿经脱敏后不超过 16,000 字符时，回传原 actor 修正，不持久化模型原文。最多三个候选时，真实 Critic 首轮与第二轮复核使用同一紧凑格式；第二轮保留补证 Findings、原评审与零补证容量。紧凑 Critic 每项因果检查可引用最多四条 Evidence，允许联合证据；引用有效性、七项检查和完整候选覆盖校验不变。

产品硬截止默认 120 秒，工具默认最多 10 秒，都可收紧；请求不能提高服务端上限。新诊断默认全局 **16 次远端模型请求**、8 次逻辑工具调用，每 Investigator 最多 3 次逻辑工具调用。9 是工具种类数，不是调用次数；旧 run 继续使用已保存的预算。

下面按每路每轮一次工具请求、一次读取结果并输出 findings 的模型请求估算，不含重试：

| 路径 | 模型请求数 |
| --- | --- |
| Lead + 三路第一轮 + Critic | 1 + 3×2 + 1 = 8 |
| 上述路径 + 一路补证 + Critic 复审 | 8 + 2 + 1 = 11 |
| 上述路径 + 三路补证 + Critic 复审 | 8 + 3×2 + 1 = 15 |

因此原 8 次上限没有给典型三路路径留下补证空间。16 是本项目按可达路径选取的初始值，不是 HolmesGPT 的推荐值或实测最优值；也不保证任意连续查询、重试和两轮三路调查都能在 120s／token 上限内完成。

模型请求计入 SDK tool continuation、重放产生的远端请求、重试和纠错。输入估算与输出上限先原子预留，返回后按 usage 结算，防止并行超售；没有 usage 的失败保留保守预算占用并标为未知，不记成免费。

输入估算按同角色已知 usage 向上或向下校准；关闭查询工具后，仍计入结构化输出工具的传输 schema。实际 usage 高于单次预留时，只能在锁内使用尚未分配的总预算余额补差，不能占用其他在途请求的预留；余额不足则拒绝结果并记录真实用量。输入只能估算，远端已发生的超额消耗不能撤回，因此预算上限不等于供应商账单的绝对上限。已知失败请求计入实际 Token 汇总，未知占用与已知用量分开统计。

每次请求最多预留 8,192 个输出 tokens，Critic 最多 16,384，并受剩余总预算约束；Critic 多候选七项审查曾连续触及 2,048 上限而被截断。未知 usage 按本次预留扣账，实际账单用量仍标为未知。SDK 缺失 usage 或只返回全零占位值时也按未知处理。中断恢复在没有首个 Checkpoint 时同样恢复已用预算，不能重置额度。

启动调查及继续可选查询前，按当前活动 Investigator 各至少一次无工具收尾、后续 Critic／复审至少一次请求保留次数和可行输入输出额度；并行分支共用现有原子预算检查，不能各自花掉同一份余量。只够收尾时停止提供工具，要求模型给 findings 和未解决缺口。补证不足以完成取证与复审时不启动，Critic 在可用预算内给最终决定；必需输入、模型失败或实际截止时间仍使收尾不可行时显式失败，不用确定性代码补写诊断。

调用 Critic 前明确告知是否仍能补证；不能补证时要求本次直接输出最终决定和未解决缺口。若模型仍只请求补证而未给有效终态，按既有输出校验／纠错规则处理，不能由服务端将 needs_evidence 自动改成 conclude 或 inconclusive。

| 路径 | 规则 |
| --- | --- |
| 工具 | 首次加最多 1 次重试，仅 transport／rate_limit；裸 timeout、无效参数、取消和归属错误不重试。复用逻辑幂等身份，不重复占逻辑工具次数 |
| 模型操作 | 首次加最多 3 次重试，最多 4 次外层尝试；transport／rate_limit、局部请求 timeout、可修复格式错误适用。指数退避基础 5s、上限 30s，不能越过总截止时间 |
| 结构化纠错 | 宽松验证阶段每个操作最多三次，无新工具，占上述 3 次重试额度，不能额外产生第五次尝试；由原输出 actor 纠正，默认 Critic，不暗中切换 Lead |
| SDK／Provider | 内置重试为 0，由现有持久化协调器统一处理；远端模型重放仍逐次计入模型次数和 tokens，成功工具结果复用 |

格式纠错达到上述上限仍不合法即失败；错误反馈指出无效引用、遗漏最终裁决等具体合同要求，不能通过增加额度放过非法 Evidence。非法 finding／candidate 可按现有校验丢弃并记录原因，但不能把任意语义错误都当成可重试格式错误；纠错不能由确定性代码添加根因。整个 Run timeout、取消、预算耗尽、认证、持久化或配置完整性错误不重试。尝试和纠错次数保存到运行记录，恢复不清零。

### 状态与恢复

| 情况 | 结果 |
| --- | --- |
| 必需节点完成且有足够证据 | completed + complete |
| 非关键 Provider／某路调查失败，剩余证据仍支持结论 | completed + partial，展示失败和缺口 |
| Agent 判断证据不足或冲突 | completed + inconclusive，无根因 |
| Lead 规划失败、全部第一轮调查失败、必需 Critic／补证执行失败、最终输出或持久化错误 | failed，无权威诊断 |
| 补证查询为空或来源不可用，但任务正常结束 | Critic 复审；关键缺口无法关闭则 inconclusive |
| 截止时间到且没有有效终态提交 | failed，原因 timeout |
| 用户取消已生效 | cancelled，不被迟到回包改成完成 |

首次进入 running 时保存开始时间和绝对截止时间，排队时间不计。阶段、重试、停机与恢复不重置时间或已消耗预算。只在 interrupted、原截止时间未到且仍有预算时人工恢复；否则新建关联诊断，不称为原 run 的恢复。

保留 SQLite 事务、单 writer、lease／attempt 检查、事件、Checkpoint 和幂等提交。配置写入 run 后不可随意更换；已提交证据不可覆盖；旧 attempt、取消和终态后的迟到结果不能污染诊断。创建失败不留无限 pending，旧记录重跑失败不改源记录。

启动之外持续审计过期 lease，保证快速重启时尚未到期的旧 lease 后续也能进入 interrupted，不自动恢复。关闭数据库前回收后台任务。SSE 按持久化 event ID 续传与去重，终态可重放；无效 cursor 或历史缺失要明确告知。

用现有输出目录保存一份配置记录：案例清单与数据版本、模型／端点、代码版本和相关未提交改动、prompt、预算与重试参数。模型和数据在同一组比较中保持一致；需要改参数时另存一组结果，不混合统计。无需额外签名、逐层 hash 或 clean HEAD 门槛；运行时原有的完整性和能力校验继续生效。

2026-09-16 用户要求先提高预算跑完所有案例，再按实际消耗确定预算。当前为宽松预算验证轮：共 60 个完整诊断和最多 30 个追加裁决，配额合计最多 13,800,000 tokens、3,240 次远端模型请求；单次远端请求超时为 120s，能力预检单次为 180s。实际费用按 usage 记录，不能宣称这是账单绝对上限。完成后分别统计各角色和配置的 Token、请求、工具、时长及失败原因，再选择有余量的预算复核；不把当前上限当作最终产品预算。此前 60,000／120s 和更早批次原样保留，不混算、不删除失败项。

离线完整路径测试和本地 canary 使用 100,000 token 的测试额度，隔离 SDK 编排与恢复正确性；小预算关闭工具、输入放不下、未知 usage 扣账另有边界测试。这些测试不证明真实模型能在 60,000 token 内跑完三路两轮，也不产生真实效果指标。现有端点能力检查的探测请求另记，不混入上述诊断配额或效果统计。未取得实际端点计价时只报告 tokens／请求数，金额标为未知。

按 case 交替 Single／Multi-Critic 的先后顺序，避免一方总在同一时段运行。两个分析都复用同一份 Multi-Critic 结果，不为了比较 Lead 重新跑上游。保存预测后再评分，答案不进入诊断进程、工具或模型上下文；数据不足时如实说明，不用合成案例替换真实样本。

### 如何比较 Lead

额外 Lead 只选择、排序或放弃已被 Critic 接受的候选，不能创建根因、调用工具或改写证据。输入与 Critic 使用相同事实和审查，去掉 Critic 最终发布顺序、结论摘要及展示 rank，候选采用相同的中性输入顺序，避免直接照抄答案。

原诊断没有有效快照时记录原因，仍计入全部 30 个案例；另报有快照子集的结果及样本数。Lead 失败或 inconclusive 算错。记录改对、改错、均对、均错，以及顺序变化、放弃候选和额外失败；事件标志可能重叠，不能相加作为准确率分母。

Lead 得到额外预算，报告应分开写上游成本和 Lead 增量。只测到裁决阶段收益，不能称为等成本比较或完整 Multi-Lead 的端到端实测；上游耗时加 Lead 耗时只是估算，不代表产品 120s 内完成。实验结果不自动切换产品默认架构。

支持引用与反证分开检查，不能要求反证也“支持根因”。final_decision.evidence_ids 只是聚合引用，沿用候选／assessment 的明确关系；只说明上下文的引用不进入支持度分母。全报告完整性必须检查全部相关引用，不能只导出候选的支持列表。

第二轮不新增候选意味着第一轮漏掉的根因无法靠最终排序补救，这是本版的明确召回限制。先用候选覆盖与裁决错误统计判断问题落在哪一段，再决定后续是否值得允许修订候选；本版不预先增加新一轮规划。候选匹配与答案只存在于离线评分代码，不能进入共享诊断路径或 Agent 上下文。

先核对本次预测的证据，再读取答案评分；OB30 历史调试或答案暴露仍注明。保留配置记录、逐例预测／失败、证据检查和汇总报告即可，复用现有脚本，不增加审核平台。单纯重算评分可复用预测；重新调用模型另存结果，保留原失败和额外成本，不挑最好结果。

全部预定案例都有可核对结果、评分正确且没有答案泄露，即完成本次评测；**不要求准确率必须提升，负结果也有价值。** 中断或缺案例时报告实际数量，不能宣称完成 30-case 评测。报告注明开发集、模型、预算、样本数及限制。

## 7. 怎样算完成

- Critic 的真实模型路径与测试替身使用同一输出规则；默认没有额外 Lead 终态调用，提前停止有真实记录。
- 构造展示 rank=A,B、最终决定=B,A 的案例，报告、API、前端、重放及评测全部以 B 为 Top1；非法引用和候选被拒绝，旧记录仍可读。
- 摘要包含必需引用和省略信息；跨 run 证据不能混入；第二轮完成“工具→Evidence→findings→Critic”链路；同源证据不被数量规则声称独立。
- 用真实 SDK 的 fake endpoint 验证同一路在本轮内根据截断提示缩小查询、继续取证后输出 findings，以及从已入库证据投影省略明细；分别检查归属、限长和预算。脚本化三路两轮各取证一次的 15 次请求路径能完成，第 16 次可用余量和第 17 次拒绝另行验证；小预算时停工具并收尾，必需输入放不下时显式失败。这些只证明执行路径，不证明真实模型效果或 120s 成功率。
- 在 SQLite 上验证并发预算、重试与纠错次数、快速重启、租约过期、人工恢复、取消、迟到结果、幂等、SSE 续传和关闭清理。
- 适用的代码检查、回归、Runtime acceptance 与前端构建通过；未运行项和原因如实列出。不涉及 Tempo 的修改无需增加 Docker 集成验证。
- 完成上述 30-case 对照并形成真实报告。只有工程检查通过时写“工程已验证，效果评测未完成”。

项目介绍保留五项能力，说明 Critic 最终裁决、人工恢复受原时间与剩余预算限制，以及效果数据来自指定条件下的开发样本。
